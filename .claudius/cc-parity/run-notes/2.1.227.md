## Summary

Between 2.1.222 and 2.1.227 upstream shipped a large batch of engine/CLI
work — gateway spend-limit warnings, cross-session `SendMessage`,
self-hosted runners, sandbox credential masking, managed-settings
merge fixes, `/code-review` becoming the canonical alias of `/review` —
almost all of which is engine-side and lands in Claudius automatically
once the SDK updater bumps `@anthropic-ai/claude-agent-sdk`. After
auditing every non-bug-fix entry against Claudius's actual code (not
just the changelog text — several entries required reading
`lib/server/plugins.ts`, `lib/server/feedback-store.ts`, and the live
Claude Code docs to confirm whether Claudius reimplements the
underlying mechanism or fully delegates it to the SDK), exactly one
product-surface gap turned up: the CLI's slash-command menu now bolds
matched filter characters instead of leaving them unstyled, and
Claudius's own `SlashCommandPicker` had never highlighted matches at
all (the other two clauses of that same entry — "blue marks only the
selected row" and "emoji/accented names keep their glyphs" — were
already true here, since Claudius never recolored per-row text and
renders unicode natively in the browser). That's the one bucket-B item
shipped this release. The headline risk to flag for review is the
gateway spend-limit item: it's classified bucket A on the assumption
that upstream will add matching fields to `SDKRateLimitInfo`, but the
currently-installed SDK type has no such fields yet, so that
assumption is unverified — see Risks.

## Implemented (bucket B)

- `[extend: chat composer slash-command picker] Bold matched filter characters in SlashCommandPicker` — added `fuzzySlashMatchIndices()` (`lib/shared/slash-commands.ts`), a pure helper returning the Unicode code-point positions in a command name that matched the typed filter, under the same prefix-then-subsequence rule the picker's existing `fuzzyScore` ranking uses. `SlashCommandPicker.tsx` gained a `HighlightedCommandName` component that collapses those positions into contiguous runs and renders each run as one `font-semibold` `<span>` in place of the plain `{c.name}` text. Rejected alternative: recoloring matched characters (e.g. with `text-[var(--accent)]`, matching the CLI's *old* behavior) instead of bolding — rejected because the changelog explicitly frames this as the CLI moving away from recolor toward bold, Claudius's picker never recolored matches in the first place (so recoloring would move backward relative to upstream's actual new state), and the accent color is already used for the leading `/` glyph in each row — reusing it for matched substrings would visually collide with that existing framing element.
  - **Caught in adversarial review:** the first cut split `name` with `.split("")` (UTF-16 code units) and rendered one `<span>` per character. Both a spawned skeptic agent and an independent unmerged prior attempt (found via `git log --all`, commit `136e7f3`, from an abandoned earlier pipeline run) flagged the same bug: `.split("")` cuts a surrogate-pair emoji or an NFD base+combining-accent sequence across two DOM nodes, which *reintroduces* the exact glyph-breaking regression the changelog's "emoji or accented names keep their glyphs" clause is about avoiding — and the per-character `<span>` wrapping doesn't match any existing emphasis idiom in `components/chat/` (emphasis elsewhere is always a whole run in one element). Fixed by switching to `Array.from(name)` (code-point iteration) and collapsing matched indices into contiguous runs before rendering, each as a single `<span>`. Two regression unit tests were added for this.

## Risks / follow-ups

- **Bucket-B item (slash-picker highlight):** alternative considered — recoloring matched characters with the accent color instead of bolding them. Rejected: see the "Implemented" bullet above for the full reasoning (matches upstream's *old* behavior, not its new one; would collide visually with the existing accent-colored `/` glyph).
- **Gateway spend-limit warning (2.1.225), classified bucket A:** this rests on an unverified assumption. Claudius's rate-limit pill already mirrors `SDKRateLimitInfo` field-by-field (see `components/chat/SystemPill.tsx`), but the currently-installed `@anthropic-ai/claude-agent-sdk` (0.3.238) type has no cap-name/operator-message fields to mirror yet — so today this is a no-op, not a confirmed pass-through. If a future SDK bump adds those fields to a *different* shape than the existing mirror expects (or exposes them only through a side channel instead of `SDKRateLimitInfo`), the rate-limit pill will need a small follow-up patch. A human should re-check this the next time the SDK updater lands a version whose `SDKRateLimitInfo` changed.
- **Workspace trust prompt for `claude agents` (2.1.225), classified bucket C:** maximal alternative considered — build a "trust this workspace?" confirmation modal in Claudius's new-workspace flow, mirroring VS Code's folder-trust dialog. Rejected as the conservative call because Claudius's workspace registration is already an explicit, deliberate user action (unlike a CLI process that can `cd` into any directory ad hoc) — the workspace list itself is the trust boundary. Revisit if Claudius ever grows a feature analogous to `claude agents` (managing agents that run on directories the user didn't explicitly register).
- **Pre-existing marketplace-settings modeling mismatch (surfaced while investigating the 2.1.223 wildcard item, not caused by it):** Claudius's `strictKnownMarketplaces` is a `boolean` toggle (`lib/server/plugins.ts`, `app/plugins/page.tsx`), while upstream's actual setting of the same name is an array of `{source, repo}` allowlist entries (confirmed via `https://code.claude.com/docs/en/settings#strictknownmarketplaces`). This predates the 2.1.222→2.1.227 window (the code cites "CC 2.1.221 parity") and reshaping it into an array-based allowlist editor is a bigger migration than anything actually new in this release — flagging for a human to scope as a dedicated follow-up rather than folding into this run.
- **`/code-review` alias + effort-level memory (2.1.223), classified bucket A:** conservative assumption — since Claudius's `review` slash command is `handler: "sdk"` (literal text forwarded, no native argument parsing on Claudius's side), "reuses the level you typed last" is assumed to be argument/skill-resolution behavior living entirely inside the forwarded SDK/skill invocation, not something Claudius's own composer needs to remember. The maximal alternative — add a small native, localStorage-backed "last review level" default in Claudius itself (analogous to `useRateLimitWarningPct`), pre-filling `/review`'s `argsHint` — was rejected as speculative scope-creep on a thin changelog line, per the "never invent features" rule. If a future release's docs or a live-SDK probe show level-memory is actually a *client*-side (CLI TUI) responsibility rather than skill-internal, this should be revisited as a real bucket-B item.
