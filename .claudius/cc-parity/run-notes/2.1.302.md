## Summary

_(Draft — finalized after implementation.)_ Claude Code 2.1.302 is mostly engine, cloud-routine, Claude Tag and terminal work. Claudius plans six bucket-B items, all extending existing screens: a "last run didn't start" banner on the Schedule page, scheduled runs that died recorded as failed, subagent cards that stop pulsing while the stream is disconnected, a size/regular-file guard on the Files preview route, empty code fences rendered as code blocks, and "Connection lost" / "Server error" wording when a session fails to start.

### Bucket B — reimplemented in Claudius

- `[B — reimplement in Claudius] [Cloud sessions] Added a banner on a routine's page that says why its last run didn't start, such as your organization reaching its limit on concurrent cloud sessions`
  - **Claudius analog.** Scheduled jobs (`lib/server/scheduler.ts`, Schedule page `app/[workspaceId]/schedule/page.tsx`).
  - **Gap.** The one recorded skip (`note: "previous_run_in_progress"`, `scheduler.ts:141-153`) only appears as raw text in a run row; the job header never says why the last fire didn't run. A workspace folder deleted after the job was saved is only checked on save (`app/api/schedule/[id]/route.ts:44-49`), so the fire throws and is logged as a generic error instead of "didn't start".
  - **Plan.** Record `lastSkipReason` / `lastSkipAt` on the job when a fire is skipped (previous run still going; folder missing at fire time), clear it when a run starts, and show an amber banner at the top of the job detail with readable text.
- `[B — reimplement in Claudius] [Cloud sessions] Fixed routine runs showing as Completed after their cloud session stopped unexpectedly, and as Cancelled when archived before they started, instead of failed`
  - **Gap.** A run's status starts as `"success"` and stays there if the agent stream ends without a `result` message (`scheduler.ts:177`). If the Claudius server dies mid-run, the run stays `running` in `runs.jsonl` forever; nothing on boot cleans it up (`scheduler.ts:72-79`), so the page shows "Live" and polls every 2 s indefinitely. (Claudius never produces `cancelled`, so the "archived before start" half has no copy.)
  - **Plan.** No result → `error` with note `session_ended_without_result`. On boot, runs left `running` from an earlier process (started before this process did, and not in `liveRuns`) become `error` / `interrupted`, and the job's `lastStatus` follows.
- `[B — reimplement in Claudius] [Remote Control] Fixed a subagent's pane spinning forever in a Remote Control session after your computer goes offline; it now says Remote Control is disconnected`
  - **Claudius analog.** When the SSE stream drops, `streamStatus` becomes `"reconnecting"` (`lib/client/use-session.ts:1216`), but only `StatusLine` reads it (`ChatSurface.tsx:2300`). Running subagent cards keep pulsing with "Subagent working…" (`components/chat/TaskBlock.tsx:160-193`).
  - **Plan.** Thread the stream state to `TaskBlock`; while reconnecting, a running subagent shows a still dot and "Disconnected — reconnecting…" instead of the pulse.
- `[B — reimplement in Claudius] Fixed the Read tool loading an image file of any size, or a pipe or device named like an image, entirely into memory; image sources over 128 MB are now refused`
  - **Claudius analog.** The HTML/asset preview route `app/api/workspaces/[id]/files/preview/[...path]/route.ts:84` calls `fs.readFile(target)` with no `stat`, no `isFile()` check and no size cap — a FIFO named `x.png` in the workspace hangs the request, and a huge file is loaded whole into memory. (The sibling `files?serve=1` route and `/api/local-image` already check `isFile()` and cap images at 10 MB.)
  - **Plan.** `stat` first; refuse non-regular files (404) and anything over 128 MB (413), inline at the sink per the CodeQL rules.
- `[B — reimplement in Claudius] [VSCode] Fixed text after an unclosed code block in a list showing as plain text while a reply streams, then turning into code` — **adjacent fix, not a mirror**
  - **Exact upstream case: not present.** mdast experiments show CommonMark already closes an unclosed fence at the end of its container, so partial and completed text yield the same `code` node in lists, bullets and at top level (`components/chat/Markdown.tsx`, one `<Markdown>` per text block, re-parsed on each delta).
  - **Adjacent flip on the same surface.** A fence with no language and no body yet (` ``` ` just streamed) renders as an empty *inline* code chip and only becomes a block when the first body line arrives; a completed empty fence stays a chip. Cause: the inline-vs-block check `!String(children).includes("\n")` (`Markdown.tsx:283`).
  - **Plan.** Decide block-vs-inline from whether the code element sits inside `<pre>` (a context set by the `pre` renderer), not from a newline.
- `[B — reimplement in Claudius] [Cloud sessions] Improved the error shown when a cloud session fails to start: it now says "Connection lost" or "Server error" instead of "Something went wrong"`
  - **Claudius analog.** `createSession` (`lib/client/use-session.ts:5228-5270`) shows the browser's raw `TypeError` text ("Failed to fetch") when the server can't be reached, and `create session failed: <detail>` for any HTTP failure.
  - **Plan.** Network failure → "create session failed: connection lost — couldn't reach Claudius"; 5xx → "create session failed: server error (<status>)…" with the route's detail kept.

### Not mirrored — Claudius surface checked, no own copy of the bug

  - Claudius already has the `idleCompaction` Settings catalog row ("Context & compaction", `app/settings/page.tsx:1098`, added by SDK 0.3.290/0.3.292) with the engine's exact description.
  - The notice is unreachable in Claudius: the engine's idle compactor only arms when `e6()` is true — interactive, or an entrypoint in its host set (`claude-vscode`, `claude-desktop`, `remote*`, …). The SDK's `sdk-ts` entrypoint is not in it, and Claudius sets no `CLAUDE_CODE_ENTRYPOINT`.
- `[A — already via SDK updater] Fixed /autocompact and /effort saving to the wrong model when a gateway names Opus 4 or 4.1 with a prefix, such as anthropic/claude-opus-4-1`
  - Claudius's effort goes through the SDK's `updateSettings({ effortLevel })` (`lib/server/session.ts:5826-5846`), so the engine picks the model key. The auto-compact window editor writes whatever model key the user types (`lib/shared/auto-compact-window.ts:68-89`). `canonicalModelId` is not start-anchored (`lib/shared/advisor.ts:378-380`), so prefixed ids already resolve for display. Two cosmetic prefix gaps are under Risks.
- `[A — already via SDK updater] [Cloud sessions] Fixed a cloud session's cost and usage restarting from zero after the session resumed in a new process`
  - Claudius seeds each new process from the persisted `session_usage` row (`seedUsageBaseline`, `session.ts:8420-8475`) and adds the live process's totals on top (`currentUsageTotals`, `:8370-8372`); a drop in cost/turns is treated as a process reset (`:1445-1448`). No own copy of the bug.
- `[A — already via SDK updater] [Cloud sessions] Fixed "Rewind to here" failing on every message except the newest in cloud sessions`
  - Each user bubble forks at its own uuid (`components/chat/UserMessage.tsx:200-204` → `/api/sessions/fork` `upToMessageId`), which is the uuid the SDK writes to the transcript (`session.ts:4122-4134`).
- `[A — already via SDK updater] [Cloud sessions] Fixed an open cloud session sometimes not showing messages sent from another device until you reloaded the page`
  - Every user message is broadcast to all SSE subscribers (`session.ts:4293-4302`) and merged by uuid on the client (`use-session.ts:3906-3925`), so a second tab sees it live.
- `[A — already via SDK updater] [Cloud sessions] Fixed a scheduled routine run that failed partway being run again from the start an hour or more later`
  - Claudius's scheduler has no retry; `lastRunAt` is saved before the agent starts (`scheduler.ts:164-165`) and every re-arm steps past now (`lib/shared/cron.ts:115`), so an interrupted run isn't repeated.
- `[A — already via SDK updater] [Cloud sessions] Fixed the pull request status bar … flipping a pull request with merge conflicts back to ready while GitHub rechecked it`
  - Claudius's PR badge never asks for `mergeable` (`lib/server/pr-status.ts:52`) and shows only state, draft and checks (`lib/shared/pr-badge.ts`), so there is no conflict state to flip.
- `[A — already via SDK updater] [Cloud sessions] Fixed the diff view in cloud sessions missing changes or failing to load after the session's GitHub repository was renamed or moved`
  - The diff route runs local git on the workspace root (`app/api/workspaces/[id]/git/diff/route.ts:24`); no `owner/repo` is stored.
- `[A — already via SDK updater] Fixed plugin marketplaces re-cloning on every refresh, and newly installed git plugins showing version "unknown", when git defaults to the reftable ref format`
  - Claudius never clones marketplaces or installs plugins itself: install sends `/plugin install` to the engine (`lib/client/usePlugins.ts:207`), versions come from the SDK's `reload_plugins` objects (`lib/server/plugins.ts:193`), and nothing reads `.git/HEAD` / `refs/` / `packed-refs` directly (the only `refs/heads` uses are `git for-each-ref` / `show-ref`, `lib/server/git.ts:732`, `:828-838`).
- `[A — already via SDK updater] Fixed worktree isolation refusing to create or resume worktrees under git 2.56 or later when a stray .git file points at a directory that doesn't exist`
  - Claudius never parses `.git` pointer files. Fork worktrees run git (`lib/server/fork-worktrees.ts:88-98`), and with a dangling `gitdir:` git itself exits 128 ("not a git repository"), so the fork falls back to sharing the checkout; resume only checks the directory exists (`fork-worktrees.ts:155-168`). The silent-fallback wording is under Risks.
- `[A — already via SDK updater] Fixed MCP servers showing no tools, or every tool call failing, when the server negotiates protocol version 2026-07-28 but omits resultType, ttlMs or cacheScope`
