## Summary

Claude Code 2.1.325 is mostly engine and CLI work: a long list of permission and sandbox hardening, MCP-task and subagent fixes, sign-in and credential fixes, and terminal UI polish. Almost all of it reaches Claudius through the bundled engine (SDK 0.3.325 already lands on this branch), or applies only to the terminal, VS Code, cloud or Slack hosts. Claudius reimplements one item, the new "plugins can run code on your computer, with access to your files and shell" copy. The engine draws it only in its terminal plugin dialogs, so Claudius now shows the engine's exact text in its own `/plugins` surfaces: the long install warning on the install form, the one-liner at the top of the catalog, and the add-marketplace note under the marketplace add form. Two Claudius-relevant entries are deliberately left as `[skip — ambiguous]` with evidence, for a human call: subagent plan approval changing the main session's mode in `Session.resolvePlan`, and the DLP-block `/rewind` hint, which the SDK gives Claudius no reliable way to detect. Headline review question: is an always-visible note on the install form, plus a note under the marketplace add form that appears once a source is typed, the right browser translation of the CLI's confirmation dialogs? Claudius adds a marketplace in one click and has no confirm step.

## Risks / follow-ups

- **Plugin trust warnings: shape call.** Shipped: inline notes (conservative). Maximal: a confirmation step before marketplace add and before catalog installs, with "Trust marketplace and continue" / "Install" buttons that copy the CLI and VS Code dialogs. Not built, because Claudius's add/install is one click by design and the changelog only changes copy. If reviewers want the gate, the strings in `lib/shared/plugin-trust.ts` are ready to use in a dialog.
- **Plugin trust warnings: copy length.** The long install warning is kept word for word (three lines of muted text under the section intro). The adversarial check suggested shortening it and moving the "Anthropic does not control…" sentence into the "What can I install?" disclosure. Not done, to keep the engine's wording; easy to change if it reads as too heavy.
- **`[skip — ambiguous]` Subagent plan approval vs main-session mode.** `Session.resolvePlan` (`lib/server/session.ts` ~L4241) treats every `ExitPlanMode` as the main session's. It sets `this.permissionMode = "acceptEdits"`, bumps `permissionModeSeq`, persists `permissionModeRecord("acceptEdits")` (which resume reads), broadcasts `mode_changed`, arms `planAwaitingVerify`, and returns `updatedPermissions: [{ type: "setMode", mode: "acceptEdits", destination: "session" }]`. `PendingPlan` never records `ctx.agentID`, so a subagent's approved plan (e.g. a custom agent with `permissionMode: plan`) can move a main session that was in `default`/`bypassPermissions`/`plan` to `acceptEdits`. That is the Claudius-side relative of CC's "session going back to an earlier permission mode after a subagent's plan was approved". Not fixed, because `sdk.d.ts` (`PermissionUpdate`/`PermissionUpdateDestination`, ~L2714–2727) doesn't say whether a `session`-destination `setMode` from a subagent's `canUseTool` applies to the main session or to the asking subagent. If it is the subagent's only way out of plan mode, dropping it would strand the subagent. Suggested fix once confirmed: carry `agentId` on `PendingPlan`, and for agent-originated plans skip the local main-session changes (and the `setMode`, if the engine lifts the subagent's plan mode itself). Cover it with a pure result-builder unit test.
- **`[skip — ambiguous]` DLP-block `/rewind` hint.** In the 2.1.325 engine, the dim line "To continue in this session, run /rewind, pick the message with the blocked content, choose Restore conversation, then change it before you send it again, or run /clear to start over. Until you do, new messages may be blocked too." is drawn by the TUI only when the internal `apiError === "dlp_request_denied"`. `SDKAssistantMessage.error` (`sdk.d.ts:3942`) carries only `invalid_request`, and the text is `API Error: <server message>`, so Claudius can't recognise the case without guessing at server wording. If the SDK later exposes `apiError` (or an `SDKAssistantMessageError` value for it), the hint belongs under the assistant error bubble with a link to Claudius's `/rewind` (the ↺ buttons) and `/clear`.
- **Scheduled jobs and skills with `allowed-tools`/hooks.** From 2.1.325 the engine asks before a scheduled task runs such a skill. Claudius's scheduler runs with `permissionMode: "auto"` + `permissionPrompts: "none"` (`lib/server/scheduler.ts:315-321`), so that ask is denied at once (Claude is told there is no approval surface). A scheduled job that used to run such a skill unattended will now skip it unless `Skill(name)` is in `permissions.allow`. Worth a line in the Schedule UI or docs if users report it.
- **Background MCP task questions.** CC now holds a background MCP task's question until the draft is sent and makes Esc mean "answer later". The SDK's `ElicitationRequest` has no task/background marker, so `components/chat/McpElicitationPrompt.tsx` still opens every elicitation straight away and maps Esc to `cancel`. Revisit if the SDK adds a marker.

It also creates `docs/sdk-updates/0.3.246`, `0.3.251`, `0.3.261`, `0.3.267` and `0.3.271`, which were never committed. None of that churn is in this PR: it was reverted.
