## Summary

2.1.257 is mostly engine-side (auto mode's Containment Escape classifier,
subagent-model env-var forcing, gateway/enterprise auth plumbing, VSCode
extension chrome) or CLI-terminal-only (TUI rendering/input perf, `/btw`
keybindings, statusline/notification-queue internals) — none of that needs
Claudius code. Two settings rows (`timeFormat`/`timeZone`) were already
absorbed as config-passthrough by the SDK-migration stage of this same
combined run (see `.claudius/sdk-updater/run-notes/0.3.257.md`) and are not
re-touched here. Three genuine bucket-B items shipped this release, all
small, targeted extensions of screens Claudius already has: (1) a
**"Block reads outside working directories"** toggle on `/permissions`,
mirroring the CLI's new `permissions.blockReadsOutsideWorkingDirectories`
— Claudius has no one-time-prompt UI to match the CLI's auto-mode prompt,
so the underlying setting is exposed as a plain per-scope checkbox instead;
(2) **`/add-dir` now refuses UNC shares and `/net/<host>` automounts**
before ever writing them into `additionalDirectories`, closing a real gap
(the route had zero path validation); (3) two more **GitHub/Slack emoji
shortcode aliases** (`satisfied`, `collision`) added to the existing alias
table established for 2.1.217/2.1.221 parity.

**Headline risk to flag for review:** the "Block reads outside working
directories" toggle writes a real `Settings.permissions` key that the SDK
reads directly off disk for project/local scope (confirmed via
`session.ts`'s `settingSources unset ⇒ all sources` comment — same
delivery path as the pre-existing `additionalDirectories`/`defaultMode`
fields, which get no special forwarding either) — so it is a real feature,
not a placebo. But Claudius has no equivalent of the CLI's *one-time
auto-mode prompt* that also sets this key interactively; only the
persistent settings toggle was built. See "## Risks / follow-ups" for the
alternative considered and rejected.

## Risks / follow-ups

- **"Block reads outside working directories" ships as a persistent toggle only, not a one-time prompt.** The CLI's version is a *reactive* one-time prompt shown at the moment of the first out-of-workspace read, with "block" as one of its two options. The maximal-parity shape would be a Claudius-side interception the first time a `Read`/`Grep`/`Glob`/LSP call targets a path outside the working directories, offering an inline "Block future reads outside working directories?" choice inside the existing permission-prompt UI (`PermissionPrompt.tsx`). That needs the ability to detect "outside working directories" client/server-side before the tool call resolves, which no existing Claudius code path does today (Claudius doesn't pre-classify tool-call targets against workspace roots). Went with the conservative shape — a discoverable persistent toggle in Settings, consistent with how `additionalDirectories` is already exposed on the same page — rather than build new tool-call interception logic for one setting. Flag for a follow-up if there's demand for the reactive/one-time-prompt version.
- **`blockReadsOutsideWorkingDirectories` at "user" scope has the same `CLAUDE_CONFIG_DIR` caveat as every other field in `PermissionRules`.** Per `session.ts`'s own comment on `settingSources`, an active account-switcher profile can re-point `CLAUDE_CONFIG_DIR`, so a value written to `~/.claude/settings.json` via `readSettings("user")` may not be the file the SDK actually loads under that profile. This is pre-existing behavior shared by `allow`/`ask`/`deny`/`defaultMode`/`additionalDirectories` (none of them get profile-aware forwarding either) — not a regression introduced here, but worth folding into that field's eventual fix rather than patched one setting at a time.
- **`/add-dir` network-path validation is scoped to the one write path the changelog names** (`/api/settings/additional-dirs`, i.e. `/add-dir` and the `additionalDirectories` settings-file key). `components/workspaces/WorkspaceForm.tsx` has a *separate* code path that writes `defaults.additionalDirectories` onto the DB-backed `Workspace` record (not `.claude/settings.json`) — that path still accepts network paths unvalidated. Conservative interpretation: the changelog explicitly names `--add-dir`/`/add-dir`/`additionalDirectories` (the settings-file key), which maps cleanly to the one route; the workspace-defaults form is a distinct Claudius-only feature with no CLI equivalent, so widening the fix there would be scope invention rather than parity. Flagged as a follow-up if the same hardening is wanted there.
- **Emoji alias list intentionally left `:telephone:` untouched** (already canonical, already accepted) rather than treating the changelog's example list as exhaustive — see the classification entry above. If upstream's actual alias table for this release turns out to include more than `satisfied`/`collision`/`telephone`, this pass under-ships; the changelog's own "…" is the ambiguity, and no `gh api`/docs source for the exact upstream table was available (Claude Code's source isn't public) — conservative reading chosen deliberately, documented per the "never invent features" rule.
- **`/doctor` stale-sandbox-mask-file warning marked C rather than B** — a judgment call: Claudius's own `/doctor` is a real, independently-built reimplementation (unlike `/effort`/`/fork`, which are thin SDK forwards), so it's the kind of surface that usually gets bucket-B treatment. But the specific check is diagnosing an implementation artifact (mask files) of the SDK's own sandbox mechanism, which Claudius doesn't manage the lifecycle of at all (`Options.sandbox` is a fixed literal, no filesystem inspection of sandbox internals anywhere in the codebase) — building a check for files Claudius never creates or knows the location/format of would be inventing a feature, not shipping parity. Flagging in case a future sandbox-management surface changes this calculus.
- None of the enterprise/gateway/Bedrock/Vertex/Foundry/managed-settings/Cowork entries were implemented — confirmed via `rg` that Claudius only ever passes these through as env vars or `/doctor` provider-detection strings (`app/api/doctor/route.ts`), never reimplements the auth/transport logic itself.
