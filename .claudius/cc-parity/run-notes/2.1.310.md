## Summary

Claude Code 2.1.310 is mostly engine and product-cloud work. The engine changes are Monitor on Bedrock/Vertex/Foundry, a gateway retry without the effort beta, cleanupPeriodDays, compaction after "Prompt is too long", Windows hook quoting, AppArmor wording for `/sandbox`, and the elicitation-timeout error. They reach Claudius through the SDK bump already on this branch. The cloud, Claude Tag, Code Review and VS Code entries are surfaces Claudius doesn't have. One fix touches a surface Claudius owns, so it is reimplemented: **file permission prompts now show where a symlink leads.** The engine resolves the link for its own terminal card but doesn't send the target through `canUseTool`. Claudius's browser card therefore showed only the link path, and approving a Read of an innocent-looking `notes.txt` could read a file outside the project. Claudius now resolves the link on the server (`lstat` + `realpath` against the session cwd and additional directories) and adds an amber row to the permission modal using Claude Code's wording. Points to review: the scope goes beyond the changelog's "read" to Edit/Write/NotebookEdit, matching what the engine's own card does; only a symlinked *final* path component is flagged, not a symlinked parent directory; and the permission card for file tools now goes out after a short async step.

## Implemented (bucket B)

- `[extend: chat permission modal]` Symlink target on file permission prompts (CC 2.1.310 "file read permission prompts not showing where a symbolic link leads").
  - **Server.** `canUseTool` in `lib/server/session.ts` calls the new `resolvePermissionSymlink` (`lib/server/permission-symlink.ts`) for Read, Edit, Write and NotebookEdit. If the requested path is itself a symlink, it `realpath`s the target, checks the target against the session cwd plus `additionalDirectories`, and adds `symlink: { target, outsideWorkingDirs, operation }` to the `permission_request` event (type in `lib/shared/events.ts`). The field is set on `meta`, so the reconnect re-emit and `/pending-prompts` carry it too. Other tools still park synchronously. If the turn is aborted during the lookup, the request is denied as "Aborted" and no card is parked.
  - **UI.** `components/chat/PermissionPrompt.tsx` shows an amber `Link2` row under the title, styled like the hook-reason row and using Claude Code's wording: "This will read/modify X (outside working directory) via a symlink" or "Symlink target: X". The target goes through `visualizeInvisibleUnicode` and counts toward the hidden-characters banner.
  - Rejected alternative: showing the target only inside the collapsed "Tool input" JSON. That is the same hidden state the upstream fix removed, so the row sits in the always-visible header instead. Also rejected: a new screen or a separate settings toggle. This is a small, display-only addition to an existing modal.

## Risks / follow-ups

- **Scope beyond the changelog: Edit/Write/NotebookEdit are included.** The conservative reading of the changelog is Read only. The engine's own card (`buildFilePermissionDescriptor` in the bundled CLI) already uses `operationType` to switch between "read" and "modify", so Claude Code shows the target on write prompts too. Claudius showed it on neither, and covering only reads would leave write prompts with the same gap. Narrowing to Read is a one-line change in the `FILE_TOOLS` map.
- **Only the final path component is checked (`lstat`).** A path under a symlinked *parent directory* (`project/vendor -> /elsewhere`, then Read `project/vendor/x`) gets no row. The fuller alternative is to compare `realpath(path)` with the lexical path. It was not built because on macOS `/tmp` and `/var/folders` are links into `/private`, so that comparison would warn on almost every temp-dir path unless both sides are normalised. A follow-up could compare `realpath(dirname)` against `realpath(cwd)` to catch parent links without the false alarm.
- **Grep/Glob `path` not covered.** They read directories rather than one file, and the changelog says "file read permission prompts". Not built.
- **"Working directory" means the session cwd plus `additionalDirectories`.** Directories granted during the session via `/add-dir` or a permission update aren't in Claudius's `additionalDirectories`, so a link into one of them would be labelled "(outside working directory)". The worst case is an overly cautious label on a display-only row.
- **The card is deferred for file tools.** The permission card for Read/Edit/Write/NotebookEdit is broadcast after an `lstat` (plus `realpath`s when it is a link) instead of synchronously. If two such prompts arrive within the same millisecond, they could be queued in the other order. Errors are caught, and the card still goes out without the row.
- **Shape alternative for the UI:** the row could be a badge in the header chip strip, next to the Subagent and MCP badges. It was not, because the target path is long and is the main thing to read. A full-width row, like the hook-reason row, keeps it readable.
