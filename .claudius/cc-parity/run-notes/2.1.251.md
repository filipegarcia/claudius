## Summary

2.1.251 is mostly engine/CLI plumbing: new `PreModelSwitch`/`PostModelSwitch`
hook events, a batch of security fixes (symlink-swap TOCTOU on file tools,
plugin-path traversal, managed-settings tracing/logging bypasses), sandbox
approval-gating changes, and a long tail of CLI-TUI and terminal-only
polish. Two entries are genuine product-surface (bucket B) additions and
both extend Claudius's existing "Session cost & usage" overlay (opened via
`/cost` · `/usage` · `/stats`), which already tracks token/cost totals and
claude.ai plan rate-limit windows: a **prompt-cache line** (hit ratio /
misses) and a **gateway spend-limit bar**. Both shipped this release, and
both were revised after an adversarial UX-fit pass flagged three problems
with the first draft: the prompt-cache section duplicated raw token counts
already shown in the stats grid above it, a "warm/cold" badge derived from
session-cumulative (not per-turn) data would misleadingly stay pinned to
"warm" after a single cache hit, and the new `spendLimit` field was nested
inside `rateLimits` in a way that forced a special-case filter everywhere
that object is treated as a homogeneous list of percentage windows. All
three were fixed (see "Implemented" and Risks). The headline risk to flag
for review: the spend-limit bar's field shape (`rate_limits.spend_limit`)
is **not yet published** in any `@anthropic-ai/claude-agent-sdk` `.d.ts` as
of this writing (checked 0.3.251, the latest published version) — the
parsing code is a best-effort guess at the shape, wired defensively so it
activates automatically once the real field ships, but it may silently
never fire if the eventual field names differ from the guess. See Risks for
the alternative considered.

- `[extend: CostOverlay ("Session cost & usage" overlay, opened via /cost · /usage · /stats)] Prompt-cache line (hit ratio, misses)` — added a "Prompt cache" section to `components/overlays/CostOverlay.tsx`, backed by a new pure helper `lib/shared/prompt-cache.ts` (`computePromptCacheStats`) that derives the stats from `SessionUsage`'s existing `inputTokens`/`cacheReadInputTokens`/`cacheCreationInputTokens` totals — no new server field needed (see classification above for why). The section renders only the two derived ratios; an adversarial review caught that the first draft also repeated the raw cache-read/cache-write token counts already shown in the stats grid above (same numbers, one screen apart) and a "warm/cold" badge that — derived from session-cumulative rather than per-turn data — would stay pinned to "warm" after a single cache hit and read as live status when it wasn't. Both were dropped; the helper still computes and exports `warm`/`tokensRecached`/`cacheWriteTokens` (kept for completeness/testability) but the UI intentionally doesn't render them. Files: `lib/shared/prompt-cache.ts` (new), `components/overlays/CostOverlay.tsx`, `tests/unit/prompt-cache.test.ts` (new). Rejected alternative: a new dedicated route/panel — overkill for two derived numbers that belong right next to the cache stats they're computed from; a new screen would fragment cost info the overlay already centralizes.
- `[extend: CostOverlay] Gateway spend-limit bar` — added a "Gateway spend limit" bar to the overlay's existing Plan section, alongside the percentage rate-limit windows, sourced from a new optional `spendLimit` field on `PlanUsageEvent`/`PlanRateLimits`. Files: `lib/shared/events.ts`, `lib/client/types.ts`, `lib/server/session.ts` (parses `rate_limits.spend_limit` defensively via a type cast, since it's absent from the SDK's published response type), `lib/client/use-session.ts`, `components/overlays/CostOverlay.tsx`. ## Risks / follow-ups

- **Spend-limit field shape is a guess, not a fact.** `rate_limits.spend_limit` does not exist in any published `@anthropic-ai/claude-agent-sdk` `.d.ts` as of 0.3.251 (the latest version at review time) — confirmed by fetching and grepping it. The parsed shape (`{limit_usd, used_usd, utilization, currency}`) is inferred by analogy to the sibling `extra_usage` object (`{monthly_limit, used_credits, utilization, currency}`), not confirmed from any spec or docs page. If the real field uses different key names, the parsing silently never fires (safe failure mode — the bar just never appears) rather than crashing; a human should re-verify the shape once the SDK actually publishes it, and adjust `lib/server/session.ts`'s `spendLimitRaw` cast accordingly.
- **Prompt-cache "warm/cold" is session-cumulative, not per-turn — and, after adversarial review, not shown as a badge at all.** Claudius only retains cumulative `SessionUsage` totals (no per-turn cache breakdown), so a warm/cold flag here could only mean "this session has had at least one cache hit so far," not "the model's cache was warm on the most recent turn" (closer to what the CLI's live `/cost` line likely means, and to the `prompt_cache_warm` boolean now available on `PreModelSwitch`/hook payloads). The first draft shipped this as a badge anyway; an adversarial review correctly flagged that it would misrepresent itself as live status. Final shape: the helper still computes `warm` (kept for tests/future use) but the UI surfaces only the hit-ratio percentage, which conveys the same "how cache-effective has this session been" signal without the false liveness cue. The maximal alternative — plumb a new per-turn SSE field for a true last-turn warm/cold flag — was rejected as overkill for what's ultimately one line in an overlay.
- **`/schedule`'s MCP-cloud-routine caveat (skipped as ambiguous).** Whether Claudius's local cron-based `/schedule` needs an analogous MCP-availability caveat is unresolved — Claudius's scheduled runs currently use the full workspace session context (MCP included), so the upstream limitation may simply not apply. A human familiar with `lib/server/scheduler-store.ts`'s actual MCP wiring should confirm whether scheduled runs can silently lose MCP access in some path (e.g. background/detached execution) before ruling this out permanently.
- **"Message @name…" placeholder (skipped as ambiguous).** Deferred rather than built because the feature it polishes — messaging a specific background subagent or fork directly from its transcript view — doesn't exist in Claudius today. Building that underlying surface (composer scoped to a specific subagent, with `@name` addressing) would be a much larger bucket-B feature in its own right; a future release should treat "can I reply to a specific subagent from its transcript" as its own audit item rather than bootstrapping it from this thin placeholder-text entry.
- None of the two shipped bucket-B items required a new SSE event type — both compose onto the existing `plan_usage` event and `SessionUsage` totals, so there's no new replay-buffer or reconnect-semantics surface to review beyond what `plan_usage`/`PlanUsageUnavailableEvent` already handle.
- An adversarial UX-fit review (a fresh agent instructed to argue the implementation was the wrong shape, not just check it compiled) was run against the first draft and surfaced the three fixes folded into "Implemented" above (duplicate stats, misleading warm badge, awkward `spendLimit` nesting). It found no further issues with putting both additions in the overlay rather than the Cost page, or with the disclaimer-based disambiguation from `LimitsPanel`.
