# Claude Code parity 2.1.247 → 2.1.248

## Summary

2.1.248 is mostly engine/CLI-side: cross-session messaging expands to more
auth backends, several settings/managed-config diagnostics land, and a pile
of terminal-UI/Windows/VSCode fixes ship — all either arrive automatically
via the SDK bump already on this branch (see the combined-mode header; SDK
0.3.247→0.3.248 landed in `a9bdd4d`/`1ee0d5f` just before this pass) or
don't translate to a browser app. One genuine bucket-B item surfaced after
auditing: `--restricted` / `CLAUDE_CODE_RESTRICTED=1`, a CLI launch flag
that locks a session down to no command/code-execution tools, no
`WebFetch`, no `bypassPermissions`, and no local settings-file loading.
The SDK doesn't expose this flag, but every primitive it needs
(`disallowedTools`, `permissionMode`, a `cwd`/`additionalDirectories`
boundary, a per-workspace defaults store with an existing settings screen)
already exists in Claudius, so it was shipped as a `restrictedMode` toggle
on the workspace settings screen. Headline risk to flag for review: is a
per-workspace boolean the right granularity, or should this be a
per-session override at launch time (see Risks). `experimental.cacheTtl`
per-agent frontmatter was investigated and found genuinely unreachable
today — the installed SDK's `AgentDefinition` type has no such field, so
UI for it would be inert; documented as a follow-up instead of shipped.

## Implemented (bucket B)

- `[extend: workspace settings] --restricted / CLAUDE_CODE_RESTRICTED=1 → "Restricted mode" toggle` —
  added `restrictedMode?: boolean` to `WorkspaceDefaults`
  (`lib/server/workspaces-store.ts`), wired into session construction in
  `lib/server/session.ts` (blocks Bash/BashOutput/KillBash/WebFetch via

  permission-mode dropdown. Rejected alternative: a new dedicated
  "security" screen — overkill for a single boolean that's a direct
  sibling of the permission-mode control already on the workspace
  defaults screen.

## Risks / follow-ups

- `restrictedMode` is a per-workspace default, not a per-session launch
  flag (unlike the CLI's `--restricted`, which is per-invocation). Chose
  the workspace-level shape because that's where Claudius's only existing
  analogous control (`permissionMode`) already lives, and because
  workspace defaults already flow into new sessions via
  `POST /api/sessions`. Alternative considered: a per-session toggle in
  the session-creation flow — rejected for this pass because there's no
  existing per-session security-posture affordance to extend (would be a
  `[new screen]`-weight addition for one boolean); worth revisiting if
  users want to flip it session-by-session rather than per workspace.
- `experimental.cacheTtl` agent frontmatter: not shipped — the installed
  SDK's `AgentDefinition` type has no such field yet
  (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts`, checked at
  0.3.248). Conservative reading (documented here, not built): once the
  SDK adds it, add `cacheTtl`/`experimental` to the allow-list in
  `lib/server/db-agents.ts`'s `coerceAgentDefinition()` and a badge in
  `app/[workspaceId]/agents/page.tsx`'s sidebar, following the exact
  pattern already used for `effort`/`memory`/`maxTurns`. Maximal reading
  that was rejected: build the badge now against the raw frontmatter
  textarea regardless of SDK support — rejected because the SDK would
  silently ignore the field, making the UI a lie.
- Server-managed settings diagnostics and `/usage-credits` were both
  marked "no reachable Claudius surface" (folded into the `[C —
  CLI/terminal only]` tag) because the audits found concretely that
  Claudius has no managed-settings fetch path and no Enterprise-Console
  admin-request hook — not because the changelog entries themselves were
  unclear. If Claudius ever grows an org-admin/Console integration, both
  are worth re-auditing.
- `--restricted`'s tool-block list (`Bash`, `BashOutput`, `KillBash`,
  `WebFetch`) was chosen to match the changelog's stated intent ("removes
  the built-in tools that run commands or code and WebFetch"); Claudius
  doesn't have a code-execution tool distinct from `Bash`, so the list is
  shorter than the CLI's. The CLI flag also supports re-allowing specific
  blocked tools via `--tools`; Claudius's `restrictedMode` has no such
  escape hatch today — it's all-or-nothing. Worth adding if a user asks
  for a middle ground.
