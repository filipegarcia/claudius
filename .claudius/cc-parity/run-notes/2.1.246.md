## Summary

Claude Code 2.1.246 is almost entirely bug fixes. Of the substantive
entries, Claudius reimplements three as bucket B, all shipped this release:
a new lint warning on `/permissions` for ambiguous Bash wildcard-before-
subcommand allow rules; an "Auto mode" tab on `/permissions` exposing the
`autoMode.{environment,allow,soft_deny,hard_deny}` classifier configuration
(the classifier's *decisions* are engine-side and arrive via the SDK; only
its configuration surface is product-side); and a per-turn live-elapsed +
wall-clock completion-time indicator in the chat status line. The headline
risk is the Auto mode tab — it's the largest, newest surface this release,
the one whose four-structured-sections shape is most likely to warrant a
different call from a human reviewer, and the one built furthest ahead of
direct product feedback (see Risks).

## Risks / follow-ups

- Auto mode tab: this is the largest bucket-B item and the most likely to need reviewer correction on shape — it exposes four freeform prose-string lists plus `$defaults` semantics that mirror the CLI closely. Alternative considered and rejected: a single free-text JSON editor for the whole `autoMode` block instead of four structured sections — less discoverable, but meaningfully less code and closer to how `/settings`' `JsonRow` already handles arbitrary object/array settings values. Went with the structured version because Auto mode is exactly the kind of feature a user would want labeled, in-context descriptions for (four semantically distinct rule classes), matching the page's existing per-kind `RuleColumn` pattern.
- `/cd` (marked C): the conservative reading is "N/A, Claudius's architecture avoids this bug class by construction" (each workspace is its own session, created with settings already loaded). The maximal reading would be giving a single Claudius session a genuine "switch this session's cwd live, reload its settings/hooks/MCP/skills/agents in place" affordance distinct from workspace-switching — a much bigger architectural change not clearly requested by this changelog entry, and one that would need its own design pass (e.g. what happens to in-flight tool calls, the transcript, and the URL). Flagging in case a reviewer disagrees with the conservative read.
- Subagent maxTurns "partial" status (marked C): if the SDK later exposes a per-subagent maxTurns/partial flag on Task results, Claudius's `TaskBlock.tsx` status-chip UI (`pending/running/completed/failed/killed/stopped`) is the natural place to add a `partial` chip — worth revisiting once that SDK surface exists. Not implemented here because there is currently no such signal to key off of, and Claudius has no `SendMessage`-to-a-subagent continuation mechanism to pair it with.
- `/goal` idle check-in cap (marked C): ambiguous whether "idle sessions" here refers to something Claudius's `/goal` should eventually grow (an autonomous background-continuation loop) — flagging since Claudius's `/goal` is otherwise feature-complete relative to upstream absent this piece. Disambiguation attempted via changelog text alone and a `code.claude.com` docs pass focused on Auto mode; no dedicated docs page was found for this specific idle-check-in mechanic within the time budget of this run.
- `/code-review` autonomous-start expansion (marked A): the conservative reading treats multi-cloud-gateway self-invocation eligibility as pure engine-side gating. If a future SDK version surfaces this as a `query()` option Claudius has to opt into explicitly (rather than it being unconditionally engine-decided), this classification should be revisited.
- StatusLine capacity: while wiring the turn-duration chips, `tests/e2e/focus-mode.spec.ts` started failing — a real, reproducible bug, not flakiness. Measured with a throwaway Playwright probe: the header row's own box is ~880px wide in that test's scenario (workspace chip + long session id + cost chip + notification bell all present), but the `ml-auto` chip cluster wants ~700px past its start position, ending ~212px past the row's right edge. The row's `clip-path` hides that overhang visually, but the clipped-yet-still-laid-out DOM elements geometrically collided with the right-rail's real "Notifications" button, so Playwright's actionability check correctly refused to click the (invisible, overlapped) Focus toggle. This means **the row was already at/near capacity before this release** — adding any new always-visible chip content was enough to push real interactive controls (Focus, the mode selector) into the clipped/overlapping zone. Fix applied: the two new chips are the LAST items in the cluster (order-wise "cheapest to lose first"), so under crowding *they* silently clip instead of Focus/Mode — verified by direct measurement that Focus's bounding box is back within the row's bounds. Follow-up worth a human's attention: this is a pre-existing latent fragility in `StatusLine.tsx`'s overflow handling (the row can want more width than it has even at the `@3xl` "full labels" tier, independent of anything in this release) that a future pass should address properly (e.g. an explicit priority-ordered collapse, or `overflow-x` handling that doesn't let clipped elements retain a live hit-box) rather than every new chip having to reason about being "last in line."
