## Summary

2.1.275 is a small release for Claudius's purposes: most of the changelog is
either engine-side (already arrives via the SDK bump on this same branch,
or is a tool-description/wire-format change Claudius renders generically)
or belongs to a different Anthropic product surface entirely (VS Code
extension, Claude Tag/Slack, Claude Code on the web, Code Review bot,
Artifact web-publishing) that this browser-based terminal-Claude-Code clone
has no analogue for. Four items are genuine bucket-B product-surface gaps
and were shipped this release: (1) a "send all queued messages now"
action wired to Ctrl+Enter on the QueueIndicator strip, mirroring the CLI's
new send-now key; (2) the `/status` overlay now shows the signed-in
account, closing a pre-existing gap where the slash command's own
description promised account info it never rendered; (3) a
`syncClaudeAiSkills` settings toggle, completing a follow-up the 0.3.246 SDK
run had explicitly flagged and left for later; (4) an optional marketplace-
source field on the Plugins page's Install form, composing the new
`--marketplace <source>` flag into the same passthrough command Claudius
already sends. The headline risk to flag for review: item (1) intentionally
does **not** implement the full "sent messages show gray until the model
receives them" half of the CLI feature — Claudius's queued-message styling
already satisfies most of that intent, and extending it to every optimistic
send bubble would touch the most heavily-used code path in the app
(`use-session.ts`'s `send()`/broadcast pipeline) for a sub-200ms cosmetic
window. See Risks for the full alternative considered.

## Risks / follow-ups

- **Send-now key — the gray-until-received styling was deliberately not
  built.** The maximal reading of the changelog entry is "every optimistic
  user bubble renders grayed out until the server confirms receipt via SSE
  echo." Claudius's queued messages already render muted/dashed in the
  QueueIndicator strip, which covers most of the user-facing intent; the
  remaining gap is a normal (non-queued) send's optimistic bubble, which
  today appears at full opacity from the moment `use-session.ts`'s
  `send()` calls `setMessages` — a window of roughly one network
  round-trip (tens to a couple hundred ms) before the server confirms
  dispatch. Implementing the maximal version means changing the rollback
  branch of `send()` and adding a `pending` flag to `DisplayMessage` /
  `UserMessage.tsx`, touching the single most call-frequency-heavy path in
  the client (every message send, in every session). Chose the
  conservative shape — ship the interrupt-and-flush action and its
  keyboard/button affordances, skip the cosmetic styling — given the
  risk/value ratio for a release-review pass with no human in the loop to
  catch a subtle regression in that path. Flagging explicitly so a human
  can decide whether the maximal version is worth a dedicated follow-up.
- **`ctrl+x ctrl+s` chord dropped.** Only `ctrl+enter` was implemented.
  The two-key Emacs-style chord is a terminal-idiom affordance (matches
  the existing double-Escape precedent in `PromptInput.tsx`, but unlike
  double-Escape, this one has no obvious browser-native parallel and no
  existing Claudius chord registry to hang it off cleanly) — judged not
  worth the added complexity for a second binding to the same action.
- **Signed-in-account "confirm before saving" — classified skip, not
  built.** Claudius's actual OAuth flow (`lib/server/account-oauth.ts`,
  `WelcomeSplash.tsx`, `app/api/accounts/oauth/route.ts`) saves the
  account and derives its label from the returned email *before* showing
  anything to the user — the literal "gateway names it, you confirm before
  saving" step doesn't exist there either, but it's a different mechanism
  (direct OAuth exchange, not a gateway-mediated sign-in) from what this
  changelog entry describes. A maximal reading would retrofit a
  confirm-before-save step onto Claudius's own OAuth flow as the closest
  analogue; rejected for this release because it touches credential-save
  logic with no upstream gateway concept to model it against — the shape
  of "what exactly is confirmed, and against what identity" is genuinely
  unclear without a gateway in the picture. Worth a follow-up if a human
  reviewer thinks the OAuth flow's save-before-confirm ordering is itself
  a UX gap independent of this changelog entry.
- **`/status` Account row — no server-side account API changes.** The row
  reuses `SessionReadyEvent.account`, which `Session.resolveAccountProfile`
  already computes for `StatusLine`'s existing badge. `toPublic()` in
  `lib/server/accounts-store.ts` (the `/api/accounts` projection) still
  strips `emailAddress`/`subscriptionType`, unchanged — `/status` only
  shows `label` (and `driftFromActive.label`), never the underlying email,
  same privacy posture as the StatusLine badge already has.
- **Plugin marketplace-source field — no attempt to validate the source
  itself.** `plugin-ref-lint.ts`'s new carve-out validates the plugin-name
  half of `<ref> --marketplace <source>` but doesn't lint `<source>` (git
  URL / npm package / local path) beyond requiring it be non-empty and
  contain no whitespace — matching how `lintMarketplaceRef` already treats
  marketplace sources elsewhere on the same page (no format validation
  beyond the owner-wildcard case). The SDK's own validation is the actual
  backstop, as it already is for every other install path on this page.
- None identified for the `syncClaudeAiSkills` toggle — it's a mechanical
  mirror of a toggle Claudius already ships for the sibling key.
- **`queue/send-all`'s dispatch ordering was reasoned through, not
  integration-tested.** The route loops the existing, already-tested
  `sendQueuedNow(uuid)` primitive over a snapshot taken after `interrupt()`.
  Because `sendQueuedNow` internally `await`s a DB pop before its
  synchronous `inputQueue.push()`, the SDK's consumer could in principle
  start draining item 0 before item 1 is even popped — reasoned that this
  is fine (Node is single-threaded, nothing else writes to `inputQueue`,
  so push-call order always matches loop-iteration order regardless of
  interleaving) and consistent with the existing single-item "Send now"
  override's own documented "asap" model (each dispatched message is its
  own sequential turn, not a merged batch). Not exercised by an
  integration test — `Session` has no existing unit-test harness in this
  codebase (it's SQLite + a live SDK subprocess; existing coverage is all
  e2e via a mocked SSE stream, which my new specs mock `queue/send-all`
  itself away from rather than exercising the real loop). Worth a human
  smoke-test against a live multi-item queue before merge.
- **`queue/send-all` discards `interrupt()`'s `stillQueued` result.** The
  existing client `interrupt()` call surfaces an info pill
  ("N queued messages will still run") from this same field; the new route
  calls `session.interrupt()` and ignores its return value. Low
  consequence here — the whole point of this action is dispatching
  everything anyway — but noted for consistency.
