## Summary

2.1.280 is dominated by TUI dialog polish, VSCode-extension parity, and
cloud (Claude Code on the web / Claude Tag / self-hosted runner) items that
have no Claudius (browser app) surface. Four real bucket-B items survive
the audit and are shipped this release: (1) Claudius's own curated
model-probe list (`app/api/models/probe/route.ts`) needed the new
`claude-opus-5-5` pin, the same treatment the 2.1.257 Fable 5.1 release
got — this is a real gap the first classification pass missed by only
checking the live `/model` picker (which does get Opus 5.5 for free from
the SDK) and not the separate hand-maintained probe list; (2) the `@`
file-mention picker's ranking fix (a filename match now outranks a
folder-only match), matching upstream exactly since Claudius owns this
ranking logic itself, not the SDK; (3) Claudius's `/skills` overlay,
previously a bare name list, now shows each skill's source and token
estimate (reusing the same `/skill-doctor` context data) plus a
click-to-toggle on/off state backed by the SDK's `Settings.skillOverrides`
key — confirmed present in the exact SDK version (0.3.278) this repo's
lockfile pins, not just a newer version that happened to be sitting in
`node_modules` from an unrelated concurrent process; (4) the composer now
strips invisible Unicode formatting/tag characters (zero-width, bidi
override, and steganographic tag-block characters) from pasted text and
from the prompt right before it's sent, with a transient footer notice —
this one shipped on a *second* pass, after an adversarial review caught
that the first pass had labeled it `[skip — ambiguous]` for what was
actually an effort reason, not an ambiguity one (a known failure mode for
this pipeline; see project memory). Headline risks to flag for review:
the skills toggle only exercises the binary "on"/"off" pair of the SDK's
four-state `skillOverrides` value (see Risks), the paste-*marking* half of
the invisible-Unicode entry (pastes over 800 chars / 2 line breaks) stays
skipped because the changelog gives no browser-visible equivalent to build
toward, and the first classification pass initially wrote off *every*
`[VSCode]` changelog bullet as not-applicable, which was wrong for two of
them (skills-dialog, invisible-Unicode) — reviewers should double-check
the remaining `[VSCode]` bullets below read correctly.

## Risks / follow-ups

- **A second adversarial review pass on the skills toggle found two real races**, fixed before finalizing: (1) `SkillsOverlay`'s mount-time GET of current overrides could resolve after a user's toggle click and clobber the toggle response's fresher state — fixed with a `hasToggledRef` guard that makes the toggle handler's own response the sole source of truth for `overrides` once any toggle has fired; (2) two different skills toggled back-to-back would issue two concurrent POSTs racing the same read-modify-write `updateSkillOverride` call (no file lock — same shape as `updatePermissions`/`updateAutoMode`, so this isn't a new pattern, just newly exposed by a UI that lets you fire two of these quickly) — fixed by disabling every toggle button while any one toggle is in flight, closing the realistic single-client case. A true cross-tab/cross-client race on the same settings file remains open, same as every other settings-updater in this codebase; not addressed here since fixing it project-wide is out of scope for this release.
- **`/api/settings/skill-overrides`'s `req.json()` isn't wrapped in try/catch** (malformed JSON → 500, not 400) and `name` has no length cap. Left as-is to match `/api/settings/permissions`'s identical, pre-existing pattern rather than introduce one route that's hardened differently from its sibling — flagging in case a future pass wants to harden the whole family of settings routes together.
- **Skills toggle only exercises "on"/"off", not the full 4-state `skillOverrides` value.** The SDK's `Settings.skillOverrides[name]` accepts `"on" | "name-only" | "user-invocable-only" | "off"`; Claudius's UI only offers a binary on/off click, matching the simplest reading of upstream's "on/off state, with a click to change the state." `isSkillOverrideValue`/`updateSkillOverride` accept all four so a hand-edited `"name-only"` value round-trips instead of being clobbered, but there's no UI affordance to *set* the middle two states. Maximal alternative: a 4-way cycling toggle or a small dropdown per row — rejected as more UI complexity than the changelog entry's plain "on/off" wording asks for; revisit if a user asks for the middle states specifically.
- **Skills toggle is project-scoped only**, not per-user or per-local. Considered `"user"` scope (a personal preference) and `"local"` scope (untracked, machine-specific) — rejected in favor of `"project"` because this mirrors `enabledPlugins`' reasoning: "which skills are on for this workspace" reads as a team-visible decision that belongs in the checked-in `.claude/settings.json`, not a personal or untracked override.
- **A prior/parallel run of this exact pipeline left a `cc-parity/2.1.280-detached-from-sdk-0.3.280` branch** with a plan-only commit (run-notes, no code) that described the same three bucket-B items in "already shipped" language despite touching zero source files. Treated as a lead list, not evidence of finished work — every claim in it (the probe-list gap, the `/skills` overlay gap, the exact `SDK.d.ts` line for `skillOverrides`) was independently re-verified against this branch's own checkout before building anything. One claim in it didn't check out: it cited `/api/sessions/[id]/context`'s `skillFrontmatter` as already used elsewhere, when in fact only `ContextOverlay.tsx` (the `/skill-doctor` overlay) consumes it — still correct that the data exists and is reusable, just attributed to the wrong specific route file initially.
- **`node_modules` had `@anthropic-ai/claude-agent-sdk@0.3.280` installed at the time of this run**, but this repo's own `bun.lock`/`package.json` pin `^0.3.278` — the 0.3.280 copy on disk was almost certainly written by a concurrent SDK-update pipeline process sharing this working tree (see project memory on the updater's shared-tree behavior), not something this branch's own install produced. Before building the skills toggle, `Settings.skillOverrides`'s presence was re-verified against the *exact* 0.3.278 `sdk.d.ts` fetched from the npm registry (not the contaminated local copy) to avoid building against a feature that might not exist in the version Claudius actually depends on.
- **Invisible-Unicode stripping shipped; paste-marking (>800 chars / >2 line breaks) still skipped.** A second-pass adversarial review flagged the original single `[skip — ambiguous]` verdict covering both halves of this entry as the "false-rationale skip" failure mode from project memory: the stated reason ("requires paste-span tracking `PromptInput.tsx` doesn't do") is an effort argument, not an ambiguity one. Split the two halves on their actual merits: invisible-Unicode stripping has a small, well-defined scope (a fixed character-class strip Claudius fully owns in its own composer) — shipped, see "Implemented" above. Paste-marking is still skipped, but now for a defensible reason: the changelog's "marked so Claude can tell it from what you typed" describes an internal VSCode-extension wire-format flag with no stated browser-visible equivalent, and inventing one (a synthetic prefix? a hidden metadata field Claude never asked for?) would be scope invention past what the entry supports. Maximal alternative considered: wrap large/multi-break pastes in an XML-ish `<pasted>` marker in the wire text sent to the model, mirroring how Claudius already marks images (`[Image #N]`) — rejected because, unlike the image case, there's no confirmed protocol Claude Code / the SDK actually reads for this, so it would just be inert text in the prompt.
- **Language-less code block styling — reclassified, not a real risk.** Originally cross-labeled `[C — CLI/terminal only]` in the classification section but "skipped as ambiguous" here; that was an internal inconsistency, not two different findings. Correct framing: `[C]` is right (TUI chrome/copy polish), and it's resolved rather than ambiguous — Claudius's `CodeBlock.tsx` already gives every fenced block, labeled or not, full chrome (border, copy button, Shiki highlight), so the readability gap the upstream fix targets doesn't exist here. No action needed; noted only so a reviewer doesn't see the two mentions and wonder which is stale.
