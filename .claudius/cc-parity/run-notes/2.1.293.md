# Claude Code parity 2.1.292 → 2.1.293

## Summary

2.1.293 adds Claude Haiku 5.5 (`claude-haiku-5-5`, now the default Haiku: $0.10/$0.50 per Mtok, $0.50/$2.50 for prompts over 100K) plus engine, terminal, mod-runtime, cloud and Slack fixes. The automated run found the Haiku pricing gap and built the fix but never committed it, so PR #293 first shipped with no parity code; that change is recovered here as written. A manual audit against the code then found three more Claudius-owned surfaces: the server-side LiteLLM pricer also priced Haiku 5.5 at the Haiku 4.5 rate, the model picker and advisor pairing table didn't know Haiku 5.5, and the Keybindings editor had no check for keys like `"ctrl+ k"`. All four ship. Headline risk: Haiku 5.5's cache rates aren't in the changelog, so both pricers assume the usual 0.1× read and 1.25× write.

## Implemented (bucket B)

- `[2.1.293] Haiku 5.5 pricing — browser estimator` — `lib/shared/cost-pricing.ts` gets its own `HAIKU_5_5` entry, matched before the generic Haiku fallback; `tests/unit/cost-pricing-new-models.test.ts`. This is the change the automated run built and left uncommitted, recovered as written. Base rate only, because the estimator has no per-request tiering. Rejected alternative: relying on the server pricer alone — the Cost page's browser-side totals read this table.
- `[2.1.293] Haiku 5.5 pricing — server pricer` — `lib/server/litellm-pricing.ts`: a `claude-haiku-5-5` entry in the bundled snapshot (`lib/server/litellm-prices.json`) with a new >100K tier next to the existing >200K one (Haiku 5.5's 100K rate also covers turns past 200K). The family fallback now prefers the longest canonical key the id contains, so provider-wrapped ids such as `us.anthropic.claude-haiku-5-5-v1:0` stop resolving to Haiku 4.5. `tests/unit/litellm-pricing-haiku-5-5.test.ts`. Rejected alternative: waiting for the runtime LiteLLM refresh — offline and pre-refresh hosts would keep billing at 10×.
- `[2.1.293] Haiku 5.5 in the model picker and advisor table` — `app/api/models/probe/route.ts` gets a pinned "Haiku 5.5" entry (Haiku 4.5 is now labelled prior generation). `lib/shared/advisor.ts` gets a `claude-haiku-5-5` executor row (Sonnet 5's advisors plus itself) and lists Haiku 5.5 as a valid advisor for Haiku 4.5, Sonnet 4.6, Sonnet 5 and Opus 4.6, from the Claude API pairing table; `tests/unit/advisor-pairing.test.ts`. Before, a Haiku 5.5 advisor was wrongly flagged as refused for those executors. Rejected alternative: none — these are lookup tables that must match the API.
- `[2.1.293] Keybinding key warning` — `lib/shared/keybinding-keys.ts` flags whitespace on either side of a `+` between two key names and suggests the fixed form; `app/[workspaceId]/keybindings/page.tsx` shows it under the binding, for the key and the chord. A lone `" "` and a trailing `"ctrl+ "` are not flagged. `tests/unit/keybinding-keys.test.ts`. Rejected alternative: auto-correcting the key on save — the CLI warns rather than rewrites, and a silent rewrite could change what a deliberate binding means.

## Risks / follow-ups

- Haiku 5.5 cache rates are assumed (0.1× read, 1.25× write of the input rate, likewise for the 100K tier); the changelog gives only the input/output rates. A LiteLLM refresh that publishes an official entry overrides the bundled one.
- The browser estimator still has no per-request tiering, so its Haiku 5.5 totals run low for turns over 100K. The server pricer tiers per turn.
- The Keybindings page can remount once after a first dev-server visit and drop unsaved rows; the e2e seeds the file through the API to avoid it. Not reproduced outside the dev server.
- Process: this PR also carries the orchestrator fix (`scripts/`): uncommitted work now fails a run instead of shipping empty, the operator's auto-memory is kept out of runs, prompts name the real branch, and models and effort are pinned (parity on `claude-opus-5-5` at high). It takes effect on the bot only after this PR merges.
