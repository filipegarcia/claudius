# SDK update 0.3.261 → 0.3.263

## Summary

0.3.262 and 0.3.263 are both bare "Updated to parity with Claude Code
v2.1.262 / v2.1.263" releases, and the orchestrator's type-surface diff
reports the public `.d.ts` as byte-identical between 0.3.261 and
0.3.263. I did not stop at that computed diff — given how many past
runs in this window were burned by trusting a "no changes" claim (see
prompt's "third failure mode"), I independently re-verified by pulling
both npm tarballs (`npm pack @anthropic-ai/claude-agent-sdk@0.3.261` /
`@0.3.263`) and diffing every shipped `.d.ts` file
(`sdk.d.ts`, `sdk-tools.d.ts`, `agentSdkTypes.d.ts`, `bridge.d.ts`,
`browser-sdk.d.ts`, `extractFromBunfs.d.ts`) directly — all six are
byte-for-byte identical except the `// Version:` header comment. The
compiled runtime bundles (`sdk.mjs`, `bridge.mjs`, `browser-sdk.js`)
did change internally (expected — that's the CLI-parity content), and
a lowercase-string-literal scan of `sdk.mjs` (imperfect — it would miss
camelCase/hyphenated literals, so it's corroborating evidence, not the
load-bearing check) shows only one new token (`"drop"`) between the two
versions. The load-bearing check is the `.d.ts` byte-identity: with
zero changed type declarations, there is no new field, exported symbol,
or control-protocol shape reachable from any API Claudius imports.
Claudius only talks to the SDK through those declared public exports
(imported in `lib/server/session.ts`, `lib/client/`, `lib/shared/`,
etc.). Net result: **no code changes were required** for this bump.
The only diff on this branch is the dependency version bump itself
(`package.json` + `bun.lock`). There is no headline risk to flag — see
"## Risks / follow-ups".
