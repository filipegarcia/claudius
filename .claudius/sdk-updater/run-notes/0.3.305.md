# SDK update 0.3.296 → 0.3.305

## Summary

The 0.3.296 → 0.3.305 window is mostly CLI-side fixes plus a handful of new public fields; earlier parity/SDK-update work on `main` had already absorbed most of the surface (`nextFireAt`, context-usage ids/`mcpInstructions`, `BUILTIN_TOOL_NAMES` guard, the four new usage-behavior keys). What was still open and is now shipped: the usage `recommendations` list (rendered in the Cost overlay as "Recommended changes", following the Day/Week toggle) and an `attributionProject` row in the Settings catalog. Everything else is `[skipped]` with an audited reason (no `startup()`/`prewarm()`/browser-SDK use, `property_order` and `fix` not reachable/actionable from our call path, managed-only `attributionProjectPolicy`). No model name, alias, default, context window or pricing tier changed in this window. Headline risk: `get_usage` is still the experimental API, so the `recommendations` shape could change without notice; the parser is defensive and the section hides itself on any failure.

## Code changes

- `lib/shared/usage-behaviors.ts` — new `UsageRecommendation` type, `recommendations` on `UsageBehaviorWindow`, and a defensive `extractRecommendations()` (drops malformed/blank entries, trims blank `detail`) called from `extractWindow()`.
- `components/overlays/CostOverlay.tsx` — `UsageBehaviorsSection` renders a "Recommended changes" list (title, `~N% of usage`, optional detail) per Day/Week window; the section now also shows when a window has recommendations but no flag over the 10% threshold.
- `app/settings/page.tsx` — `attributionProject` string row in `SDK_SETTINGS_CATALOG` (Settings → Git).
- `tests/unit/cc-parity-2.1.299-usage-behaviors.test.ts` — updated the window-shape expectation and added two recommendation-parsing specs.
- `tests/e2e/sdk-update-0.3.305-usage-recommendations.spec.ts` — new spec + screenshot.
- `tests/e2e/sdk-update-0.3.287-prompt-queue.spec.ts` — fixed a pre-existing load-dependent failure of the "URL prompt with no elicitationId" spec (failed twice in full-suite runs, passes in isolation): the mocked SSE stream ends on every `route.fulfill`, EventSource reconnects, and the mock dropped the ephemeral `mcp_elicitation_request` on reconnect, so on a loaded machine the modal vanished before the click. `mockChatBackend` gained an opt-in `replayPending` (mimicking the real server re-emitting still-pending prompts on resubscribe) used by that spec, and the click retry re-opens the link if a remount reset the "opened" state. Verified passing with a forced 15s stall before the click. Unrelated to the SDK bump.

## Risks / follow-ups

- `get_usage` is the SDK's `_EXPERIMENTAL_MAY_CHANGE` API; `recommendations` titles/details are SDK-worded text we render verbatim.
- Decision: `fix` (the SDK-provided `/effort` commands + composed prompt, sent at priority `later`) was not wired. Alternative considered: a "Fix" button in the Cost overlay that queues those messages into the session; rejected as a separate feature needing composer/queue plumbing and confirmation UX. Reasonable follow-up.
- Decision: `addPlugins` and sdk-MCP per-tool `permission_policy` have no Claudius UI to author them, so they were left unexposed rather than adding routes with no front end.
- `attributionProject` is only honoured by the CLI for claude.ai-login direct-API sessions; the row writes the setting regardless, as the description says.
