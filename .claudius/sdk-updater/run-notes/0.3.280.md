## Summary

Between 0.3.278 (the version this branch actually started from —
`package.json` already carried `^0.3.278` before this run's dependency
bump, ahead of the `--previous=0.3.274` this run was invoked with) and
0.3.280, upstream added MCP Apps tool `_meta`, an alpha `readMcpResource()`
reader, a `verbatimPrompts`/`client_composed` opt-out of prompt-attachment
expansion, a `fireReason` on scheduled task-notifications, a `'highlights'`
thinking-display mode, always-present `severity`/`is_active` on the
`SDKUsageReport` rate-limit rows, several `SlashCommand`/npm-marketplace/
Artifact-tool field additions, and assorted remote-session latency
telemetry. A four-agent parallel audit (plus direct verification) found
that most of the load-bearing items from this window — `projectConfigRoot`
(0.3.275), `SlashCommand.builtin` (0.3.277), `updateSettings('userSettings',
{effortLevel})` (0.3.277), and the resumed/forked-session cost-continuity
fix (0.3.277) — were **already implemented in a prior SDK-update cycle**,
each with a doc comment in the code citing the exact SDK version. This PR
ships two genuinely new pieces of work: (1) a small "UI" chip on `/mcp`
surfacing when an MCP tool declares an MCP-Apps `ui://` resource via the
new `_meta` field, with a Playwright spec + screenshot, and (2) `verbatimPrompts:
true` on Claudius's three host-composed, tool-less, single-turn `query()`
calls (commit-message generation, customization-description generation,
session recap) that embed raw diff/transcript text a user never typed as
that prompt — closing a latent (if minor) risk that a `@path`- or
`/command`-looking substring inside embedded diff/transcript text gets
misinterpreted as a live file mention or slash dispatch. Everything else
in the window is genuinely not applicable to Claudius's architecture (no
call site, no renderer, or an explicit "remote-hosted only" gate that
Claudius's locally-spawned CLI subprocess never satisfies) — see the
itemized audit below. **Headline risk to flag for review:** the
`verbatimPrompts` additions are conservative (all three call sites are
already `tools: []`/`maxTurns: 1`, so the lost turn-start attachment pass
costs nothing there), but they are new behavior on live code paths users
hit constantly (git commit message generation), so watch for any
regression in those three specific one-shot flows post-merge.

## Code changes

- `lib/client/useMcp.ts` — added `_meta?: Record<string, unknown>` to the
  `LiveStatus.tools[]` element type, so the new SDK 0.3.280 field
  type-checks through from `GET /api/mcp` (already forwarded raw by
  `app/api/mcp/route.ts`, no server change needed).
- `app/[workspaceId]/mcp/page.tsx` — added `mcpToolUiResourceUri()` helper
  (reads `_meta.ui.resourceUri` or the deprecated flat
  `_meta['ui/resourceUri']`) and a small "UI" chip (`LayoutPanelTop` icon,
  `data-testid="mcp-tool-ui-badge-<toolName>"`) rendered next to any tool
  in the per-server expanded tool list whose `_meta` declares a `ui://`
  resource.
- `lib/server/commit-message.ts`, `lib/server/customization-description.ts`,
  `lib/server/session-recap.ts` — added `verbatimPrompts: true` to each
  `query()` call's `options`. All three build a host-composed prompt that
  embeds raw diff or transcript text verbatim (not something the end user
  typed as that prompt); all three are already `tools: []` (or
  `canUseTool`-deny-all) + `maxTurns: 1`, so losing the turn-start
  attachment pass this option also skips costs nothing.
- `tests/e2e/sdk-update-0.3.280-mcp-tool-ui-badge.spec.ts` — new Playwright
  spec covering the chip (see New UI surfaces).
- `tests/unit/verbatim-prompts.test.ts` — new vitest spec asserting
  `verbatimPrompts: true` actually reaches `query()`'s options for the two
  lightest-weight of the three call sites above (see Tests).

## Risks / follow-ups

- **`fireReason` deferred.** Wiring Claudius's own scheduler to declare
  `scheduled-trigger`/`fireReason` provenance is a real (~15-line, multi-file)
  feature — scheduler prompt-shape change (string → streamed
  `SDKUserMessage`), a non-constant reason (cron-fire vs. manual `runNow()`),
  `CLAUDE_CODE_HOST_SCHEDULED_RUN=1` via the existing `buildQueryEnv()`
  pattern, and a client `SDKMessageOrigin` type update so it's not
  invisible in the transcript UI — not a safe drive-by for this PR. Next
  human: pick this up as its own small feature if scheduled-run provenance
  in the transcript is wanted.
- **`readMcpResource()` / MCP Apps UI rendering** is intentionally not
  built beyond the presence chip. Reading and rendering a `ui://` resource
  means (a) gating on the CLI advertising `mcp_read_resource_v1` in
  `system/init.capabilities`, and (b) a sandboxed-iframe (or equivalent)
  design for untrusted third-party HTML — a real design task, not a
  one-line addition. The chip is a safe stepping stone.
- **Pre-existing CI flake, unrelated to this migration:** PR #265's e2e
  run showed `tests/e2e/cc-parity-2.1.257-block-reads-outside-working-dirs.spec.ts`
  failing all 3 attempts (1 failed / 294 passed overall). Re-ran it
  locally in isolation and it passed cleanly (7.1s) — looks like CI
  resource contention under the full 295-spec run, not a real regression;
  not touched by this PR's diff. Flagging in case it recurs.
- **Branch reconciliation note:** this branch (`cc-parity/2.1.280`) had
  diverged from `origin/cc-parity/2.1.280` when this run started — a
  separate cc-parity pass had pushed an invisible-Unicode-paste fix and a
  version bump directly to origin while this SDK-update run's dependency
  bump commit sat only locally. Reconciled with a merge commit (not a
  rebase, per the "never rewrite history outside sdk-update/*" constraint)
  before starting the SDK audit; no conflicts, both sides touched
  `package.json`'s version field identically to `"0.3.280"`.
