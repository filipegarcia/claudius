# SDK update 0.3.248 → 0.3.250

## Summary

`0.3.249` and `0.3.250` are both bare "Updated to parity with Claude
Code v2.1.249 / v2.1.250" releases, and — unusually — this is not just
a thin prose changelog: the SDK's own type-surface diff is empty
(`sdk.d.ts` byte-identical between 0.3.248 and 0.3.250), and diffing
the actual npm tarballs shows the published JS wrapper (`sdk.mjs`,
`bridge.mjs`, `browser-sdk.js`) is byte-identical too, save for the
`"0.3.248"` → `"0.3.250"` version string itself (`cmp -l` found 6
changed bytes in `sdk.mjs`, 4 in `bridge.mjs`, 2 in `browser-sdk.js` —
each is exactly the version-string literal, nothing else). The only
things that actually changed are the per-platform native CLI binary
checksums/sizes in `manifest.json` — i.e. whatever "parity with Claude
Code v2.1.249/250" means, it lives entirely inside the compiled binary
Claudius spawns, not in any JS/TS surface we import or call against.
Given that, **no Claudius code changes are required** for this bump;
the only change is the dependency version itself. Headline risk to
flag for review: this branch (`sdk-update/0.3.248`, not
`sdk-update/0.3.250` as the run prompt describes) carries unmerged
product work from the prior 0.3.246–0.3.248 release stacked underneath
the 0.3.250 version bump commit — see "## Risks / follow-ups".

## Code changes

- No code changes required. The dependency bump itself
  (`package.json` `^0.3.248` → `^0.3.250`, `bun.lock`) is the entire
  diff for this release. Both the public type surface and the shipped
  JS wrapper are byte-identical to 0.3.248 apart from the embedded
  version string (see audit above), so there is no SDK-facing behavior
  for Claudius to adapt to.

## New UI surfaces

## Tests

  change to cover — the existing suite already exercises every SDK
  entry point Claudius uses, and those entry points are unchanged.

## Risks / follow-ups

- This branch is named `sdk-update/0.3.248`, not `sdk-update/0.3.250`
  as the run prompt describes ("The orchestrator has already: checked
  out a fresh branch `sdk-update/0.3.250`"). In practice it's a stacked
  branch: `git log` shows the 0.3.246→0.3.248 product work (MCP
  per-server tool-call timeout, desktop session cleanup-days setting,
  their e2e spec/screenshot, and the `2.1.248` cc-parity notes) already
  committed underneath the `0.3.250` version-bump commit
  (`2791ab7`). Scoped correctly (`git diff 2791ab7^..HEAD`), the
  0.3.250-specific diff is exactly `package.json` + `bun.lock`, which
  is why "## Code changes" above says none are needed — that inherited
  work is real, already-merged product code from a prior run, not
  scope creep from this one. Flagging so a reviewer isn't confused by
  branch naming when they diff against `main`.
- Because "parity with Claude Code v2.1.249/250" behaviour lives
  entirely in the native CLI binary (per the tarball audit above),
  there's no way for this run to inspect *what* changed there beyond
  the checksum move. If a future issue traces back to CLI-binary
  behaviour in this version range, the fix will need to come from
  upstream's actual release notes for Claude Code v2.1.249/250, not
  from anything visible in this SDK package.
