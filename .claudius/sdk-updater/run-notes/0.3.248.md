## Summary

0.3.248 is a small release: the changelog's single line adds a per-server
`timeout` for SDK-hosted MCP servers (`createSdkMcpServer({ timeout })`),
overriding `MCP_TOOL_TIMEOUT` for that server's tool calls. The `.d.ts` diff
adds three more identifiers not mentioned in the prose changelog: a new
`Settings.desktopSessionCleanupPeriodDays` field, an internal
`sdkMcpServerConfigs` map on the (unexported) control-protocol init
request, and a `favicon` field on the Artifact tool's input/output shapes.
We shipped two small, real changes: (1) set an explicit 10s `timeout` on
Claudius's one SDK-hosted MCP server (`claudius_goal`, which previously ran
with no bound at all since `MCP_TOOL_TIMEOUT` is never set), and (2) added
`desktopSessionCleanupPeriodDays` to the generic `SDK_SETTINGS_CATALOG`
passthrough on `/settings`, directly beside the existing `cleanupPeriodDays`
row it's a sibling of, with a new Playwright spec covering it end-to-end
and a screenshot of the row in context. The Artifact `favicon` field and
the internal `sdkMcpServerConfigs` map are both genuinely
unreachable/inapplicable — audited below. Headline risk: low — both
shipped changes are additive and match existing conventions exactly (a
settings-catalog row, an MCP-server option); the main thing worth a second
look is whether 10s is the right timeout value for the goal tool (see
Risks).

## SDK changelog highlights

- Added a per-server `timeout` for SDK-hosted MCP servers
  (`createSdkMcpServer({ timeout })`), overriding `MCP_TOOL_TIMEOUT` for
  that server's tool calls. — `[shipped]`. Claudius has exactly one
  SDK-hosted MCP server (`buildGoalMcpServer` in `lib/server/session.ts`,
  registered as `claudius_goal` with the single `report_goal_achieved`
  tool). Claudius never sets `MCP_TOOL_TIMEOUT`, so that tool call was
  previously unbounded. Set `timeout: 10_000` on the `createSdkMcpServer`
  call — the tool body only awaits a synchronous SQLite write
  (`setGoalAchieved`), so 10s is a generous defensive bound, not a tuned
  value; it exists so a stuck write can't hang a turn indefinitely.

### New declarations (type-surface diff)

- `sdk.d.ts` `CreateSdkMcpServerOptions.timeout` / `McpSdkServerConfig.timeout`
  — `[shipped]`. Same item as above; this is the field `createSdkMcpServer`
  actually exposes (the changelog bullet and this declaration are the same
  change from two angles).
- `sdk.d.ts` `SDKControlInitializeRequest.sdkMcpServerConfigs` —
  `[skipped — not exported]`. This is a `declare type` with no `export`
  keyword in `sdk.d.ts`; it's the SDK's own internal wire representation of
  the control-protocol `initialize` request, populated automatically by the
  SDK's transport layer from each server's `McpSdkServerConfig.timeout` when
  we call `createSdkMcpServer`. There is no public entry point in
  `claude-agent-sdk`'s exported surface that lets a host construct or read
  this map directly — verified by grepping `sdk.d.ts` for `export` on this
  symbol and its containing union (`SDKControlRequestInner`), neither of
  which Claudius imports. Shipping the `timeout` option above is the entire
  reachable surface of this feature.
- `sdk.d.ts` `Settings.desktopSessionCleanupPeriodDays` — `[shipped]`.
  Added as a new row in `SDK_SETTINGS_CATALOG`
  (`app/settings/page.tsx`), directly next to the existing
  `cleanupPeriodDays` row (same "Storage & sessions" section), matching the
  established pattern for surfacing new `Settings` keys as a generic
  labeled field that round-trips through `settings.json`. Not one of the
  model-identity/pricing-tier fields the second failure mode warns about —
  it's a desktop-host (Claude Desktop/Cowork) transcript-retention knob;
  Claudius isn't one of those hosts, so it never governs Claudius's own
  session cleanup (that's still `cleanupPeriodDays`), but it's still a
  legitimate `settings.json` key a Claudius user might also want to set if
  they run one of those other hosts against the same config file.
- `sdk-tools.d.ts` `ArtifactOutput.favicon` / `ArtifactInput.favicon`
  (doc-only reword: favicon is now optional on redeploy, required only on
  first publish) — `[skipped — no Artifact-tool renderer in Claudius]`.
  Audited: `rg -ni "ArtifactInput|ArtifactOutput|disableArtifact"` across
  `app/`, `components/`, and `lib/` returns zero hits outside
  `node_modules`. Claudius never special-cases the Artifact tool's
  input/output shape — any `tool_use`/`tool_result` block for it (if the
  Artifact tool is even reachable from Claudius's tool config, which itself
  isn't restricted per-tool here) falls through the same generic
  JSON-message renderer every unrecognized tool uses. A new optional string
  field on a type we never destructure requires no code change, and the
  reworded doc text is model-facing tool-description prose, not something
  Claudius echoes anywhere in its own UI copy.

## Risks / follow-ups

- The `timeout: 10_000` on `claudius_goal` is a conservative guess, not a
  measured value — `setGoalAchieved` is a synchronous SQLite write and
  should complete in low single-digit milliseconds, so 10s is meant purely
  as a "never hang the turn forever" backstop. If a future SDK change makes
  MCP tool-call timeouts user-configurable end-to-end, this is the value to
  revisit.
- `desktopSessionCleanupPeriodDays` is surfaced but inert for Claudius
  itself (Claudius isn't a desktop-host surface per the SDK's own
  definition — Claude Desktop/Cowork are). It's included purely as a
  faithful `settings.json` passthrough for users who share config between
  Claudius and one of those other hosts; nothing in Claudius reads or acts
  on it directly, matching how the existing catalog already treats several
  other host-specific keys.
- `sdkMcpServerConfigs` (the internal control-protocol map) has no public
  entry point today. If a future SDK release exports it or adds a second
  way to set it, re-audit — right now `McpSdkServerConfig.timeout` (which
  we do use) is confirmed to be the only reachable surface.
