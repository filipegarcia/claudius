# SDK update 0.3.319 → 0.3.321

## Summary

0.3.320 is a bare parity bump; 0.3.321 is a hook/permission/session-robustness release (hook `ask`/`defer` merging, `undefined` hook entries, `WarmQuery`/`SpareProcess` fixes, worktree skill reload, OOM handling) plus one public type addition: `CronDeleteOutput.endedLoopWakeup`. That field is the only change that touches Claudius behaviour. The self-paced loop rail keys wake-ups by their `ScheduleWakeup` tool_use id, so a `CronDelete` of the wake-up never matched and the chip stayed live; we now read `endedLoopWakeup` off the `CronDelete` tool result on both the client reducer and the server mirror (`trackScheduledLoops`) and flip the pending wake-up to cancelled. We also refreshed one Settings catalog description whose upstream wording changed. Headline risk: the server/client wake-up cancel is keyed on the structured `tool_use_result` payload, so it is a no-op on older SDKs (tolerant by design). No model-identity, pricing or default-model changes in this window.

## Code changes

- `lib/shared/session-loops.ts` — added `readEndedLoopWakeup(toolUseResult)`: tolerant reader (only literal `true`) for `CronDeleteOutput.endedLoopWakeup`.
- `lib/client/use-session.ts` — in the tool_result handler, when the matched tool_use is `CronDelete` and the result reports `endedLoopWakeup`, call `markWakeupsStopped` (deduped per tool_use id via `appliedWakeupStopsRef`, bounded to wake-ups armed at/before the result).
- `lib/server/session.ts` — new `pendingCronDeletes` set (cleared with the other loop state); `trackScheduledLoops` records `CronDelete` tool_use ids and, on the matching result with `endedLoopWakeup`, cancels pending wake-ups (deduped via `appliedWakeupStops`, bounded by `observedAt`).
- `app/settings/page.tsx` — refreshed the `forceLoginMethod` description to the new upstream wording.
- `tests/unit/cc-parity-2.1.311-dead-session-restart.test.ts` — the partial `Session` stub gains `pendingCronDeletes` (it calls the real `end()` which clears it).

## New UI surfaces

- No new UI surfaces this release. The only user-visible effect is an existing loop-rail/`/schedule` chip now flipping to its existing "cancelled" tone after `CronDelete` of the wake-up; no new element, so no screenshot spec. The behaviour is covered by vitest (below).

## Risks / follow-ups

- The client reducer branch is not directly unit-tested; consider extracting the tool_result loop handling into a pure reducer in a future cycle.
- Assumption: `endedLoopWakeup` always accompanies a successful `CronDelete` of the wake-up, so we cancel *all* live wake-ups armed at or before the result (a session has at most one self-paced loop). Alternative rejected: matching by wake-up id, which Claudius cannot see (wake-ups are keyed by tool_use id).
- Harness note: nothing under `scripts/sdk-update/` was edited.
