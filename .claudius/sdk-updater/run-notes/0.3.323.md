# SDK update 0.3.317 → 0.3.323

## Summary

0.3.317 → 0.3.323 is a parity-heavy window (CC 2.1.318–2.1.323). Most of its surface — `credential_expires_at`, `config_file_invalid`, `endedLoopWakeup`, `permissions.denyInsteadOfPrompting`, `disableReplyCheck`, `disableWindowsBashCommandSplit` — was already adopted by earlier CC-parity runs on `main`. What this PR adds on top of the version bump: (1) the new `managed_settings_not_delivered` startup-failure label (the union grew by a member the changelog never mentions), (2) client eviction of messages named by an assistant message's `supersedes` (0.3.323 extends it to unparseable-tool-call responses), (3) hook-wait heartbeat `tool_progress` frames (`hook-` ids) are kept out of the per-tool progress map, (4) `setMcpServers` now re-sends Claudius's in-process `claudius_goal` server, because the 0.3.323 docs state the call replaces all in-process SDK servers including those given in `mcpServers`, and (5) the managed model policy reads `machinePolicy.didNotLoad` and ORs the alpha `matchDeniedModels()` into the picker's denied-alias check. Headline risks: the `supersedes` eviction is a behaviour change for refusal fallbacks too (now per the SDK contract), and the `setMcpServers` fix could not be exercised against a live agent.

## Risks / follow-ups

- `supersedes` eviction now also applies to refusal-fallback messages (the SDK says to evict on arrival). If an eviction removes a tool_use bubble, its tool_result entry is simply orphaned and not rendered. Reviewer should eyeball a refusal fallback on a live session.
- `setMcpServers` sends a fresh `claudius_goal` instance each call. I chose a fresh instance over reusing the spawn-time one to avoid an "already connected" error; not verified live. Alternative: reuse the stored instance.
- Hook heartbeats are dropped rather than rendered as a "waiting on hook" indicator (conservative choice); a follow-up could surface them next to the spinner.
- `matchDeniedModels` is alpha and async; failures degrade to the local matcher.
- The harness under `scripts/sdk-update/` was not touched.
