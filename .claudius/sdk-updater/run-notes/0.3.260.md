## Summary

0.3.260 is a small, mostly-internal release: four new optional
latency-breakdown fields on `SDKResultSuccess` (remote-session
round-trip diagnostics), a `user_message_uuid` correlation field on
`SDKThinkingTokensMessage`, an internal `cowritten` flag + `list_types`
action on the Artifact tool's types, and four behavior fixes
(`managedSettings` `disableAutoMode` filtering, `rewindFiles()`
false-success, structured-output retry error messages, and
`rate_limit_event` re-emission cadence). We shipped one real change:
`user_message_uuid` now drives more precise attribution of live
thinking-token estimates to the correct "Thinking" row in the Activity
rail, replacing a pure recency heuristic that could mis-attribute a
stale trailing frame from an interrupted turn to a freshly-opened row
for a new send. Every other item audited to a genuine no-op for
Claudius (see below) — none of them are model-identity items, and none
required a `[skipped]` on a bare "SDK-internal" hand-wave. Headline
risk to flag: the new uuid-preference path in
`applyThinkingTokensEstimate` is covered by vitest but not by an e2e
spec, since reliably reproducing the two-overlapping-thinking-blocks
race against the real agent isn't practical in CI (see Risks).

## Code changes

- `lib/client/types.ts` — added `ToolHistoryEntry.userMessageUuid?:
  string`, the client uuid stamped from a matching `thinking_tokens`
  frame's `user_message_uuid`.
- `lib/client/idle-reconcile.ts` — `applyThinkingTokensEstimate()` now
  takes an optional third `userMessageUuid` argument. When present, it
  prefers a thinking row already stamped with a matching uuid over the
  plain "most recent open" pick, falling back to the old recency
  heuristic when no row is stamped yet or the frame carries no uuid
  (older CLI). Stamps the row with the uuid on first match.
- `lib/client/use-session.ts` — the `thinking_tokens` system-message
  handler now reads `user_message_uuid` off the raw SDK message and
  forwards it into `applyThinkingTokensEstimate`.
- `tests/unit/thinking-tokens-reducer.test.ts` — four new tests
  covering the uuid-preference path, the "no match yet → falls back to
  recency and stamps forward" path, and confirming the no-uuid call
  shape is byte-identical to the pre-0.3.260 behavior.

## New UI surfaces

- No new UI surfaces this release. The shipped change is a correctness
  fix to the *attribution* of an existing UI element (the live
  thinking-token counter on the "Thinking" row in the Activity rail,
  shipped in SDK 0.3.153) — it changes which row a given estimate lands
  on under a specific race, not anything visible in a screenshot. The
  rail's appearance, copy, and layout are unchanged.

## Tests

- vitest: 4 new specs (in the existing
  `tests/unit/thinking-tokens-reducer.test.ts` file), 0 updated
  (existing 8 specs pass unmodified against the new optional third
  parameter).
- playwright: 0 new, 0 updated. The uuid-attribution race this fixes
  (a stale trailing `thinking_tokens` frame from an interrupted turn
  landing after a new send's thinking row has already opened) requires
  sub-second control over real SDK event ordering that isn't
  practically reproducible through the mocked-SSE e2e harness or worth
  the flake risk of trying against `chromium-live`. The vitest coverage
  exercises the reducer's decision logic directly and exhaustively
  (match found / no match yet / no uuid supplied).
- Not covered: the four latency fields, `cowritten`, `list_types`, and
  the three behavior-only fixes have no Claudius call site (see
  changelog highlights), so nothing to test.

## Risks / follow-ups

- The new `userMessageUuid` attribution path is unit-tested but not
  e2e-tested (see Tests). If a future release makes the
  overlapping-thinking-blocks race easier to trigger deterministically
  (e.g. a test-only SSE injection hook), it'd be worth adding a
  regression spec then.
- If Claudius ever grows a per-turn latency/telemetry surface (a debug
  panel, a "slow turn" diagnostic), revisit the four skipped
  `SDKResultSuccess` fields (`first_content_frame_ms`,
  `first_stream_post_ms`, `first_stream_post_ack_ms`,
  `first_stream_post_wall_ms`) together with the still-unconsumed
  `request_sent_wall_ms` / `time_to_request_from_spawn_ms` /
  `warm_spare_claimed` fields already on the type — they were skipped
  purely for lack of a consumer, not because they're unreachable.
- If Claudius ever adds Artifact-tool support, revisit `cowritten` and
  `list_types` together with the rest of `ArtifactInput`/`ArtifactOutput`
  at that time rather than piecemeal.
