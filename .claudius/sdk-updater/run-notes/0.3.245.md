## Summary

`@anthropic-ai/claude-agent-sdk` 0.3.241 → 0.3.245 is a small bump on the
surface: three of the four intermediate releases (0.3.242, 0.3.244, 0.3.245)
are opaque "parity with Claude Code v2.1.24x" bumps with no itemized public
changelog, and 0.3.243 ships four itemized changes that are all SDK-internal
correctness fixes. **The prose changelog is not the whole story.** A diff of
the shipped `.d.ts` files shows this window added **17 new public
declarations**, seven of which the changelog never mentions — including two
(`modelPicker`, `modelPricing`) that are squarely model-identity and
pricing-tier surface. This PR therefore does three things: it takes the bump, it **ships the
three items in the window that Claudius should actually adopt**
(`promptCacheTtl` / `subagentPromptCacheTtl` catalog rows,
`queued_turn_count` in the QueueIndicator, `ScheduleWakeup.noop` as a
quiet-hold chip), and it **hardens the updater itself** so a future run
cannot repeat the mistake this one originally made, which was to reason from
the four-bullet changelog alone, conclude "no code changes required", and
ship a PR whose entire diff was a version bump.

Headline risk to flag for review: `queued_turn_count` fixes a real bug, not
just a missing feature. Under `queueDispatchMode: "asap"` the QueueIndicator
strip read **empty** while turns were genuinely pending, because our own
`queued_messages` table is bypassed on that path. Everything else in the
window is a verified no-op for Claudius, with the audit trail recorded below
so a reviewer can check the reasoning rather than the diff.

## SDK changelog highlights

**0.3.243** (the only release in this window with itemized changes):

- Added optional `queued_turn_count` to result messages (`SDKResultSuccess`
  / `SDKResultError`) — `[shipped]`. **Correcting an earlier draft of these
  notes**, which
  claimed Claudius "never lets more than one user message sit in the SDK's
  own streaming `inputQueue` at a time" and that the field "is always
  `0`/absent for our sessions". That is false for the `queueDispatchMode:
  "asap"` setting: `lib/server/session.ts:1613` documents it as *"skip the
  DB queue, push straight to the SDK's input pipe on every send, **even when
  a turn is in flight**"*, and `app/api/sessions/[id]/input/route.ts:82-84`
  confirms `shouldEnqueue` is false in that mode regardless of `isIdle`. The
  same applies to every "Send now" click (`sendQueuedNow()`,
  `session.ts:5865`). So the SDK-side queue is real for us and the counter
  is non-zero. This is a live gap — `session.ts:817` notes the
  QueueIndicator reflects "the server-side `queued_messages` table, **not**
  the SDK's internal queue", so in asap mode the strip read empty while N
  turns were genuinely pending. Now broadcast on `queue:updated` as
  `sdkQueuedTurns` and rendered as a non-interactive count row — once a
  message is inside the SDK's queue we no longer hold it, so edit / reorder
  / withdraw would be a lie.
- Fixed `mcp_status` reporting a remote MCP server as `connected` after its
  connection dropped; it now reports `pending` while reconnecting —
  `[skipped — pure SDK-side correctness fix we inherit]`. Verified:
  `Session.reconnectMcp` (`lib/server/session.ts` ~L4693) already documents
  and defers to this exact race, and `app/[workspaceId]/mcp/page.tsx`
  renders whatever `status.status` string the SDK reports without assuming
  transition timing. No wrapper code assumed the old buggy behaviour.
- Fixed managed `disableAllHooks` also disabling hook callbacks registered
  through the `hooks` option — `[skipped — correctness fix benefiting an
  existing call site]`. Claudius registers its worktree-detection,
  mid-turn-reminder-drain, post-write-snapshot and `CwdChanged` hooks via
  the SDK's `hooks:` option (`lib/server/session.ts` ~L2347-2449) — exactly
  the path this bug wrongly suppressed. We never set `disableAllHooks`
  ourselves, so there is nothing to change; we just stop being exposed.
- Changed Read tool PDF results: the `document` block (or page `image`
  blocks) now arrives inside `tool_result` content instead of a trailing
  `user` message — `[skipped — absorbed by existing generic rendering]`.
  Verified: `extractToolResult` (`lib/client/use-session.ts:589`) walks
  `tr.content` and concatenates only blocks carrying `.text`, silently
  skipping image/document blocks. Both the old and new shapes render
  identically. Worth noting as an *opportunity* rather than a migration:
  page images now land in the array we already walk, so rendering them is
  newly cheap.

**0.3.242 / 0.3.244 / 0.3.245** — `[skipped — opaque "parity with Claude
Code vX" bumps, no itemized public changelog]`. CLI feature-parity tracking
is the separate `scripts/cc-parity/` workstream. `bun run build`'s full
production compile passed against `sdk.d.ts` as shipped in 0.3.245.

**Type-surface additions the changelog omits.** Diffing the `.d.ts` files
shipped in the two npm tarballs surfaces 17 new top-level declarations. Each
gets a position:

- `Settings.promptCacheTtl`, `Settings.subagentPromptCacheTtl` (`'5m' | '1h'`)
  — `[shipped]`. These belong in `SDK_SETTINGS_CATALOG`
  (`app/settings/page.tsx:936`), whose own comment reads *"When the SDK
  bumps, diff this table against the new sdk.d.ts."* They are reachable
  today only through the raw "Other" JSON editor (`ClaudeSettings` has an
  `[key: string]: unknown` escape hatch at `lib/server/settings.ts:177`),
  and the SDK reads `~/.claude/settings.json` itself, so the gap was
  discoverability, not plumbing. Now two labeled enum rows under
  "Context & compaction", carrying the SDK's own descriptions.
- `Settings.modelPicker` (+ nested `options` / `model` / `label` /
  `description` / `replaceBuiltInOptions`) — `[skipped — audited]`.
  **This is model-identity surface**, so per the higher bar: audited
  `app/api/models/route.ts` (reads no settings at all — no hook exists for
  a settings-driven picker), `app/api/models/probe/route.ts`,
  `app/api/sessions/[id]/model/route.ts`, `lib/client/types.ts`, and
  `ModelPicker.tsx`. Claudius builds its picker from its own
  `STATIC_FALLBACK` + probe, not from settings. Adopting it would be a new
  feature, not a migration. It also sits directly beside `modelOverrides`,
  which `SDK_SETTINGS_CATALOG` already excludes by policy as a nested
  managed-tier object.
- `Settings.modelPricing` (+ nested `multiplier` / `overrides` / `input` /
  `output` / `cacheRead` / `cacheWrite`) — `[skipped — audited]`.
  **This is pricing-tier surface.** Audited `lib/server/litellm-pricing.ts`,
  `lib/server/litellm-prices.json` and the `/cost` page. The SDK doc states
  it is *"Only honored from managed settings … ignored in user, project,
  local and --settings sources"*, which matches the catalog's stated
  exclusion of managed/enterprise-only keys. Genuine skip — but note an
  earlier draft of these notes asserted "no item in this window touches a
  model name, capability tier, **or pricing tier**", which this falsifies.
- `Settings.managedSourcesBehavior` (`'first-wins' | 'merge'`) —
  `[skipped — managed-only]`. Sits beside `parentSettingsBehavior`, already
  excluded from the catalog on the same basis.
- `default_to_no` on the `can_use_tool` control request —
  `[skipped — not reachable]`. The SDK doc says hosts "should not pre-select
  approve when set", which Claudius's permission modal would honour. But the
  field lives only on the internal control-protocol type: the exported
  `CanUseTool` options object is **byte-identical** between 0.3.241 and
  0.3.245 (verified by diffing the signature), so the SDK drops it before
  invoking the callback we use (`session.ts:2192`). Nothing to implement
  until upstream plumbs it through. Watch item for a future bump.
- `ScheduleWakeupInput.noop` — `[shipped]`. Claudius already
  reconstructs session loops from this tool's input (`session.ts:4102` reads
  `delaySeconds` / `reason` / `prompt`; `lib/shared/session-loops.ts`) and
  renders them on `/schedule` and the Activity rail. `noop` marks quiet
  ticks that Claude Code collapses into a streak. Now rendered as a
  "quiet hold ×N" chip on both surfaces. The streak is accumulated across
  each wake-up's replacement of its predecessor, because `noop` itself is
  per-tick.
- `ReadToolOutput.artifactRead` (`{slug, ver}`) — `[skipped — no surface]`.
  Claudius has no Artifact tool surface (`rg Artifact` over `app/`,
  `components/`, `lib/` returns nothing).
- `ReadToolOutput.firstPage`, `ReadToolOutput.pages` — `[type-only]`. The
  companion shapes to the Read-PDF reshape above; absorbed by
  `extractToolResult`'s generic content walk with no code change.
- `RemoteTriggerOutput.detail`, `RemoteTriggerOutput.server_message` —
  `[skipped — no consumer]`. `components/chat/ToolCall.tsx:111` renders only
  the *input* `action` label for this tool; there is no trigger-output
  rendering for these to feed. Adopting them means building that surface
  first.
- `AgentOutput.imagesOmitted`, `imagePagesFailed`, `imagePagesFailedOmitted`,
  `documentsOmitted` — `[skipped — no consumer]`. Per-result cap counters on
  Task/Workflow output, which Claudius does not render today.
- `AgentOutput.harnessNoteCount` / `harnessTailCount` / `harnessSectionHash`
  / `handoffReviewSkipped` — `[skipped — @internal]`. All four carry an
  explicit `@internal` JSDoc marker reading "not a stable consumer field".

**Doc-only changes** (no new declaration, but real): `disableArtifact` was
deprecated in favour of `enableArtifact` purely by rewording its JSDoc, and
`enableArtifact`'s precedence rules were restated. Neither key is in
`SDK_SETTINGS_CATALOG` and Claudius has no Artifact surface, so no action.
The rest is a "CCR" → "cloud session" rename and interrupt send-gate
wording.

## Code changes

- **`scripts/sdk-update/orchestrate.ts`** — new pipeline step 6b.
  `fetchTypeSurfaceDiff()` `npm pack`s the previous version and
  `git diff --no-index`es its `.d.ts` files against the freshly-installed
  `node_modules/` copy, then `extractDeclarationChanges()` pulls out added
  declarations and drops the JSDoc prose that dominates the diff by volume.
  Brace-depth tracking separates a real new member (`modelPicker`, depth 0)
  from its inner fields (`label`, `options`, `model`) — gating on names that
  generic would pass a mention-check on incidental prose, which is worse
  than not checking. `@internal` entries are listed but exempt. The raw diff
  still ships, clipped at 400 chars/line, because doc-only changes like the
  `disableArtifact` deprecation produce no declaration.
  `validateTypeSurfaceCoverage()` joins the existing run-notes gate: a run
  whose notes never *name* a new public field opens draft + `needs-human`.
  A failed fetch yields an empty identifier list, so a registry blip can
  never become a false red gate.
- **`scripts/sdk-update/prompt.md`** — a "third failure mode: trusting the
  prose changelog" section alongside the two existing ones, citing this
  window concretely; Step 1 now requires reading both the changelog and the
  type-surface diff; the run-notes required shape and Definition of Done
  (item 6b) require a position on every new identifier; and a new
  `TYPE_SURFACE_BLOCK` placeholder section at the bottom, rendered by
  `renderPrompt()`.
- **`scripts/sdk-update/README.md`** — documents step 6b, two new
  failure-mode rows, and a note that loosening `MAX_GATED_IDENTIFIERS`
  weakens the guard.
- **`tests/unit/sdk-update-orchestrate.test.ts`** — 15 tests, below.
- **`lib/server/settings.ts` + `app/settings/page.tsx`** — `promptCacheTtl`
  and `subagentPromptCacheTtl` on `ClaudeSettings` plus two `SDK_SETTINGS_CATALOG`
  rows under "Context & compaction", carrying the SDK's own descriptions.
  Discoverability only: `ClaudeSettings` already passed unknown keys through
  and the CLI reads the same file, so there is no forwarding to add.
- **`lib/shared/events.ts` + `lib/server/session.ts` + `lib/client/use-session.ts`
  + `lib/client/types.ts`** — `queued_turn_count` is read off the result
  message into `Session.sdkQueuedTurns`, broadcast on `queue:updated` as
  `sdkQueuedTurns`, and mirrored into client state. Absent is normalised to 0
  so a stale count can't outlive the turn that reported it; the broadcast
  fires only on a change, since a result lands every turn. `sendQueueSnapshot`
  now also fires when only the SDK-side queue is non-empty — keying it off
  `queueCache` alone hid exactly the asap-mode case.
- **`components/chat/QueueIndicator.tsx` + `ChatSurface.tsx`** — the strip
  now appears when *either* queue is non-empty, with the SDK count as a
  non-interactive row. No edit / reorder / withdraw affordances: those
  messages are already inside the SDK and we no longer hold them.
- **`lib/shared/session-loops.ts` + `lib/client/types.ts` + `session.ts` +
  `use-session.ts`** — `noop` and a derived `noopStreak` on `SessionLoop` /
  `ScheduledLoop`. The streak is accumulated as each wake-up supersedes its
  predecessor, identically on both sides, because `noop` is per-tick and a
  dynamic loop chains one wake-up per turn.
- **`components/panels/widgets/ScheduledLoops.tsx` + `app/[workspaceId]/schedule/page.tsx`**
  — a "quiet hold ×N" chip on both loop surfaces.
- **`components/panels/widgets/CollapsibleSection.tsx`** — a `data-testid`
  keyed on `storageKey` so Activity-rail sections have a stable handle.
  Deliberately not `data-pane-name`: several call sites already wrap this
  component in their own `data-pane-name` div, and a duplicate would turn
  every existing `[data-pane-name="tasks"]` locator into a strict-mode
  violation.
- **No change required for the rest of the window.** Every other 0.3.243
  item and type-surface field is audited above; none needs a call-site
  change to take the bump safely.

## Risks / follow-ups

- **`notifications-multi-tab.spec.ts:199` is red on this branch and was
  already red before it** (see "## Tests"). Worth a look independently of
  this PR; it is not a regression from anything here.
- **The noop streak is reconstructed, not authoritative.** Both reducers
  derive it by inheriting from the wake-up being superseded, because the SDK
  reports `noop` per tick and never sends a run length. A session resumed
  mid-loop therefore restarts the count from the first wake-up its replay
  contains, rather than from the true beginning of the hold. Acceptable for
  an informational chip; if it ever needs to be exact, the count would have
  to be persisted alongside the loop rather than derived.
- **`sdkQueuedTurns` is only as fresh as the last result message.** It
  updates at turn boundaries, so a send made mid-turn is not reflected until
  that turn ends. The count is never *wrong*, just briefly behind — and the
  local queue rows, which do update immediately, cover the default "wait"
  mode. Watch this if the SDK ever starts coalescing our one-at-a-time
  pushes, which would change what the number means.
- **`default_to_no` is a watch item.** It is a real permission-prompt UX
  signal that Claudius would honour, but it is unreachable through the
  exported `CanUseTool` today. Re-check on the next bump that touches the
  permission path — if upstream adds it to the callback options object,
  it becomes a small, worthwhile change.
- **The new gate can go red on a legitimately large bump.**
  `MAX_GATED_IDENTIFIERS` caps coverage demand at 40 identifiers. A release
  that adds more will list them all in the prompt but gate on the first 40.
  If that ever produces friction, the fix is a better `@internal` signal
  upstream, not a wider cap — widening it re-opens exactly the hole this
  PR closes.
- **The type-surface diff costs one `npm pack` per run** (~1s, previous
  version only — the new side is already in `node_modules/`). It is
  best-effort: any failure logs, yields an empty identifier list, and the
  prompt tells Claude to read `sdk.d.ts` directly and say so in the notes.
- CLI-level parity for Claude Code v2.1.242–2.1.245 remains the separate
  `scripts/cc-parity/` workstream — intentionally out of scope here, not
  missed.
