## Summary

`@anthropic-ai/claude-agent-sdk` 0.3.241 → 0.3.245 is a small bump: three of
the four intermediate releases (0.3.242, 0.3.244, 0.3.245) are opaque
"parity with Claude Code v2.1.24x" bumps with no itemized public changelog,
and the one release with concrete items (0.3.243) ships four changes that
are all internal correctness fixes to behavior Claudius already treats
generically or already owns a parallel implementation of: a `mcp_status`
reconnect-race fix (our reconnect code already waits on `pending` rather
than assuming `connected`), a `disableAllHooks` fix that stops it from also
disabling hooks registered via the SDK's `hooks:` option (Claudius registers
its worktree/reminder/snapshot hooks that way, so this is a straight
correctness win with no call-site change), a Read-tool PDF result reshape
that moves `document`/page `image` blocks from a trailing synthetic `user`
message into the `tool_result` content array (our `extractToolResult`
already walks `tool_result.content` generically for `.text` and silently
ignores non-text blocks, so both the old and new shapes render identically),
and an optional `queued_turn_count` field on result messages (Claudius has
its own DB-backed queue — `queued_messages` / `queueCache` / `editQueuedMessage`
/ `moveQueuedMessage` — that feeds the SDK's streaming `inputQueue` one
message at a time under our own control, so the SDK's built-in command-queue
counter reflects a queueing mechanism we don't use and is always 0/absent
for us). `bun run lint`, `bun run test`, and `bun run build` are all green
against the bumped dependency with zero source changes required. Headline
risk to flag for review: this is a genuine no-code-change migration — the
audit trail for each item is recorded below so a reviewer can check the
reasoning rather than the diff.

## SDK changelog highlights

**0.3.243** (the only release in this window with itemized changes):

- Added optional `queued_turn_count` to result messages (`SDKResultSuccess`
  / `SDKResultError`, `sdk.d.ts` ~L4632/L4682) — `[skipped — Claudius owns
  its own queue, doesn't need the SDK's]`. Claudius never lets more than one
  user message sit in the SDK's own streaming `inputQueue` at a time: queued
  sends live in our `queued_messages` SQLite table (`lib/server/session.ts`
  `queueCache`, `listQueue`, `editQueuedMessage`, `moveQueuedMessage`) and we
  push the next one onto `this.inputQueue` ourselves only once the prior turn
  finishes. The SDK's own command-queue counter this field reports on is a
  queueing mechanism we bypass entirely, so it is always `0`/absent for our
  sessions and has no UI we'd wire it to.
- Fixed `mcp_status` reporting a remote MCP server as `connected` after its
  connection dropped; it now reports `pending` while reconnecting, then
  `connected`/`failed` — `[skipped — pure SDK-side correctness fix, already
  handled generically]`. `Session.reconnectMcp` (`lib/server/session.ts`
  ~L4693) already documents and defers to this exact race in its comments
  ("the SDK's status may still report `pending` immediately after this
  await, so we don't re-query and assert 'connected'") and the `/mcp` page
  (`app/[workspaceId]/mcp/page.tsx`) renders whatever `status.status` string
  the SDK reports (`pending`/`connected`/`failed`/`disabled`) without
  assuming any particular transition timing. No wrapper code assumed the old
  (buggy) always-`connected` behavior, so the fix is a pure correctness
  improvement we inherit for free.
- Fixed managed `disableAllHooks` also disabling hook callbacks registered
  through the `hooks` option (they now keep running, matching
  `allowManagedHooksOnly`) — `[skipped — correctness fix that benefits an
  existing call site, no code change needed]`. Claudius registers its
  worktree-detection, mid-turn-reminder-drain, post-write-snapshot, and
  `CwdChanged` hooks via the SDK's `hooks:` option passed into `query()`
  (`lib/server/session.ts` ~L2347-2449) — exactly the path this bug used to
  wrongly suppress when a user/managed `disableAllHooks: true` setting was
  present (`lib/server/hooks.ts` `setDisableAllHooks`). Before this fix, a
  managed `disableAllHooks` could have silently broken worktree-badge
  detection and mid-turn reminders; now it can't. We don't set
  `disableAllHooks` ourselves anywhere, so there's nothing to change —
  we just stop being exposed to the bug.
- Changed Read tool PDF results: the `document` block (or page `image`
  blocks for `pages` reads) now arrives inside the `tool_result` content
  instead of as a separate `user` message after it — `[skipped — transcript
  rendering already walks tool_result.content generically]`. `extractToolResult`
  (`lib/client/use-session.ts` ~L589) iterates `tr.content` and concatenates
  any block with a `.text` property, silently skipping blocks without one
  (image/document blocks included) — this is unchanged by whether those
  blocks arrive inside `tool_result.content` or in a trailing `user`
  message; we never special-cased "the message right after a Read
  tool_result" to pull out PDF pages. Audited `FilePreview.tsx` /
  `FileGrid.tsx` / `asset-store.ts` (which do have PDF-aware code) and
  confirmed they're for the *workspace file browser's* attachment preview,
  not for Read-tool transcript rendering — unrelated surface, untouched.

**0.3.242 / 0.3.244 / 0.3.245** — `[skipped — opaque "parity with Claude
Code vX" bumps, no itemized public changelog]`. These three releases carry

**Model-identity audit.** No item in this changelog window touches a model

## Code changes

- No code changes required. Every item in this changelog window is either
  an opaque undocumented "parity" bump (0.3.242/244/245) that `bun run
  build`'s full TypeScript compile confirms introduces no breaking type
  change reaching Claudius, or (0.3.243) an SDK-internal correctness fix
  to behavior Claudius already handles generically (`extractToolResult`'s
  content-block walk, the `/mcp` page's status-string rendering,
  `reconnectMcp`'s existing pending-race handling) or already owns a
  parallel implementation of (the app-level `queued_messages` queue vs.
  the SDK's `queued_turn_count`). `package.json` /
  `.claudius/sdk-updater/run-notes/0.3.245.md` are the only files this PR
  touches; see "## SDK changelog highlights" above for the per-item audit
  trail backing each `[skipped]` call.

## New UI surfaces

  documented change at all. `docs/sdk-updates/0.3.245/` is intentionally
  empty.

## Risks / follow-ups

- The 0.3.242/0.3.244/0.3.245 "parity with Claude Code vX" bumps carry no
  itemized public changelog, so this audit leaned on `bun run build`'s full
  TypeScript compile (zero errors against the bumped `sdk.d.ts`) plus a
  targeted `grep` of `sdk.d.ts` for model-identity and MCP/hooks/queue
  surface changes to rule out anything actionable. If Claude Code CLI
  v2.1.228 → v2.1.245 introduced user-facing behavior that isn't captured
  in the SDK's public type surface (e.g. a prompt/tool-description change
  inside the CLI binary itself), it would be caught by the separate
  `scripts/cc-parity/` workstream, not this SDK-version-bump run — flagging
  so a human knows that gap is intentionally out of scope here, not missed.
- `queued_turn_count` (SDK 0.3.243) is deliberately not wired to any
  Claudius UI (see "## SDK changelog highlights"). If a future release
  changes the SDK's own command-queue semantics in a way that starts
  interacting with our app-level queue (e.g. the SDK begins coalescing our
  single always-one-at-a-time pushes), this field would become the fastest
  way to detect that — worth a second look if queue-related behavior ever
  looks off after a later bump.
