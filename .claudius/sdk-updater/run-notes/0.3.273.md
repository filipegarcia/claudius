## Summary

0.3.273 is a small release: a new `usage_report` structured twin on the
synthetic assistant message that answers a headless `/usage`, a new
`reason: "worker_restart"` on `task_notification` for a task orphaned by a
worker-process restart, a transcript notice + bugfix around `Stop`/
`SessionStart`/`SubagentStop` hook timeouts, a browser-transport fix for a
dropped `commands_changed` push, and one new Artifact-tool output flag
(`outside_writer`). Of these, only `task_notification.reason` is both
reachable from Claudius's code paths and user-visible, so it's the only
`[shipped]` item: it's now plumbed server → SQLite → SSE → client → the
right-rail "Recent" list, which now reads `stopped (restarted)` (with an
explanatory tooltip) instead of a bare, context-free `stopped` when a
background task/subagent/workflow is orphaned by a worker restart rather
than stopped by the user or the agent. Everything else audits out as
unreachable or purely SDK/CLI-internal — see below for the per-item
reasoning, especially `usage_report` (Claudius's `/usage` slash command is
intercepted and redirected client-side before it ever reaches the SDK, so
the message this field rides on is never produced by our own dispatch).
Headline risk to flag for review: the `reason` audit trail is
best-effort — if a future SDK release adds more `task_notification.reason`
values, `TaskSnapshotEntry.reason`/`TaskInfo.reason` are typed to the
single literal `"worker_restart"` today and will need widening.

## SDK changelog highlights

- `usage_report` (`SDKAssistantMessage.usage_report`, type
  `SDKUsageReport`) `[skipped — audited, unreachable from Claudius's
  dispatch]`. Claudius's `/usage` slash command is registered with
  `handler: "native"` in `lib/shared/slash-commands.ts` and is intercepted
  entirely client-side (`app/[workspaceId]/page.tsx`'s `runNative` case
  `"usage"` → `router.push("/usage")`) — the literal text `/usage` is
  never sent to the SDK's `query()` as a prompt from Claudius's own UI, so
  the synthetic assistant message this field rides on is never produced
  through our normal dispatch. Claudius's own structured usage/rate-limit
  data (the `CostOverlay`, `plan_usage` SSE event) comes from a wholly
  separate mechanism — the `usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET()`
  control call in `lib/server/session.ts`, fired after every successful
  turn — which is unaffected by this field either way. The one
  theoretical gap is a caller hitting Claudius's session-send API
  directly with literal `/usage` text, bypassing the browser's client-side
  interception; even then this is a pure-add, optional field, and the
  SDK's own doc comment calls the assistant message's `content` text "the
  canonical fallback" — which Claudius already renders generically for
  any assistant message, so no behaviour changes either way.
- `task_notification.reason: 'worker_restart'` `[shipped]`. Plumbed
  through `lib/shared/events.ts` (`TaskSnapshotEntry.reason`),
  `lib/server/session.ts` (`captureTaskState`'s `task_notification` case),
  a new migration (`022_session_tasks_reason.sql`) +
  `lib/server/session-tasks-db.ts` (SQLite round-trip so it survives an
  idle-reap/reload), `lib/client/types.ts` (`TaskInfo.reason`),
  `lib/client/use-session.ts` (the `task_notification` reducer), and
  `components/panels/BackgroundTasksPanel.tsx` (renders `stopped
  (restarted)` with an explanatory tooltip in the Tasks/Running/Recent
  rows).
- `SDKUsageReport` and all of its inner fields (`session.*`,
  `rate_limits.limits[].*`, `rate_limits.extra_usage.*`) `[skipped — same
  reasoning as usage_report above]`. These are all nested fields of the
  parent type covered by the bullet above; none is independently
  reachable.
- Added `reason: 'worker_restart'` to `task_notification` `[shipped]` —
  same item as above (the changelog and the type-surface diff both name
  it; one implementation covers both).
- One-line transcript notice when a `Stop`/`SessionStart` hook callback
  times out `[skipped — no new type surface, no Claudius call site]`.
  This is prose the CLI now writes into its own transcript when a host's
  hook callback (any host, including Claudius's own `PreToolUse`/
  `PostToolUse`/`CwdChanged`/`PostModelSwitch` hooks or a user's
  `.claude/settings.json`-configured `Stop`/`SessionStart` hooks
  surfaced through Claudius's `/hooks` viewer, `lib/shared/hook-events.ts`)
  times out. No new field appears in the type-surface diff for it — it
  rides through the same generic `system` message path Claudius already
  has: an unrecognized subtype falls through to the catch-all
  `` `system/${subtype}` `` pill in `lib/client/use-session.ts` (see the
  `isSuppressedSystemEvent` fallback around line 4110). No code change
  needed for it to render.
- Fixed a `Stop`/`SubagentStop`/`SessionStart` hook callback timeout being
  wrongly reported as a hook failure that discarded other hooks'
  decisions; it now counts as no decision `[skipped — CLI/host-execution
  internal, no type surface change, no Claudius call site]`. This is a
  bugfix in how the CLI's own hook-execution engine scores a timed-out
  callback. Claudius registers zero `Stop`/`SessionStart`/`SubagentStop`
  hooks itself (confirmed: `lib/server/session.ts`'s `hooks:` block only
  registers `PreToolUse`, `PostToolUse`, `CwdChanged`, and
  `PostModelSwitch`) — the fix benefits any user-configured `Stop`/
  `SessionStart`/`SubagentStop` hook equally without a Claudius change.
- Fixed the browser SSE transport dropping the live slash-command list
  update (`system/commands_changed`) `[type-only — transparent fix, no
  call-site change]`. Claudius already has a `commands_changed` handler
  (`lib/client/use-session.ts` around line 4098, added for the SDK
  0.3.195 fix) that replaces the cached slash-command list outright when
  this message arrives. The bug being fixed lived entirely in the
  browser transport dropping the message before Claudius's handler ever
  saw it; the fix makes our existing handler receive what it should have
  all along, with zero code change on our side. Reflected in the
  `.d.ts` diff only as a docstring reword on `getSseLastSequenceNum`
  (browser-sdk.d.ts) — verified Claudius doesn't call
  `getSseLastSequenceNum` anywhere (`grep -rn getSseLastSequenceNum
  lib/ app/` is empty), so that doc-only change has no surface for us
  either.
- `outside_writer` (`sdk-tools.d.ts`, `ArtifactOutput.outside_writer`)
  `[skipped — no Artifact-tool call site]`. A sibling flag to the
  existing `cowritten`/`foreign` fields on the Artifact tool's output
  union. Claudius has no Artifact-tool-specific handling anywhere in the
  app (`grep -rn "cowritten\|ArtifactOutput\|outside_writer"
  lib/ app/ components/` returns nothing) — Artifact tool results render
  through the fully generic tool-result path, so `cowritten`/`foreign`
  are equally unused today and `outside_writer` doesn't change that.
- "Updated to parity with Claude Code v2.1.273" `[skipped — no
  Claudius-specific parity item named]`. No individual parity bullet to
  triage beyond what's covered above.

## Code changes

- `lib/shared/events.ts` — `TaskSnapshotEntry.reason?: "worker_restart"`,
  documented and typed to the SDK's single current literal.
- `lib/server/session.ts` — `captureTaskState`'s `task_notification`
  branch reads `msg.reason` off the raw envelope and carries it onto the
  in-memory `TaskSnapshotEntry`.
- `lib/server/db-migrations/022_session_tasks_reason.sql` — new nullable
  `reason` column on `session_tasks`, following the same convention as
  migration 018 (`ambient`).
- `lib/server/session-tasks-db.ts` — `reason` added to the row shape,
  the upsert `INSERT`/`ON CONFLICT` column list, and the `SELECT`, so a
  worker-restart orphan survives an idle-reap/reload rebuild instead of
  reverting to a bare `stopped`.
- `lib/client/types.ts` — `TaskInfo.reason?: "worker_restart"`.
- `lib/client/use-session.ts` — two separate mappings, both needed: the
  live `task_notification` reducer reads `t.reason` and carries it onto
  the client's `TaskInfo`; the `task_snapshot` rehydrate handler (the
  idle-reap/reload path, a field-by-field `TaskSnapshotEntry` →
  `TaskInfo` mapping in the same style as `resourceLinks`) also carries
  `reason` — missing this second one was caught in review: a
  worker-restart orphan would have read correctly on a live session but
  silently reverted to a bare `stopped` after a reload rebuilt the
  session from SQLite, defeating the point of migration 022.
- `components/panels/BackgroundTasksPanel.tsx` — new `taskStatusLabel`/
  `taskStatusTitle` helpers; every status pill (Tasks, Running, Recent)
  now renders `stopped (restarted)` with an explanatory `title` tooltip
  when `reason === "worker_restart"`, and plain `t.status` otherwise
  (unchanged for every other case). Each status span also gets
  `data-testid="task-status"` so e2e can target it precisely — the
  status text is a substring of the row's own full text content, so an
  untagged text-substring locator would have matched multiple ancestor
  elements under Playwright's strict mode.
- `tests/unit/session-tasks.test.ts` — round-trip coverage for `reason`
  through SQLite (migration 022) and through `Session.captureTaskState`'s
  live `task_notification` handling, mirroring the existing
  `ambient`/`resourceLinks` test pairs in the same file.
- `tests/e2e/sdk-update-0.3.273-task-notification-worker-restart.spec.ts`
  — new Playwright spec (see "## New UI surfaces").

## New UI surfaces

- The right-rail "Recent" (and, while still live, "Tasks"/"Running") row
  for a background task/subagent/workflow that was orphaned by a worker
  restart now reads `stopped (restarted)` instead of a bare `stopped`,
  with a tooltip explaining the cause. Screenshot:
  `docs/sdk-updates/0.3.273/task-notification-worker-restart.png`.
  Captured by
  `tests/e2e/sdk-update-0.3.273-task-notification-worker-restart.spec.ts`,
  which mocks a session where a backgrounded `Task` tool call's subagent
  ends via `task_notification: { status: "stopped", reason:
  "worker_restart" }`. Confirmed by reading the captured PNG: the full
  app chrome is visible (top tab strip, left workspace nav, the
  transcript with the "Kicking off the nightly report workflow…" message
  and the `Task` tool_use card reading "Stopped") and the right rail's
  "Recent" section is in frame showing "Generate the nightly re…
  stopped (restarted)" — the label in its real context, not an isolated
  crop.

## Risks / follow-ups

- `TaskSnapshotEntry.reason` / `TaskInfo.reason` are typed to the single
  literal `"worker_restart"` (the only value the SDK documents today). A
  future release adding another `task_notification.reason` value will
  need this type widened in three places (`lib/shared/events.ts`,
  `lib/client/types.ts`, and the inline cast in
  `lib/client/use-session.ts`) plus a label decision in
  `BackgroundTasksPanel.tsx` — `taskStatusLabel`/`taskStatusTitle`
  currently special-case only `worker_restart` and would silently fall
  back to a bare `stopped` for any other value until updated.
- The `usage_report` skip assumes Claudius's `/usage` slash command stays
  a client-side `native`-handler redirect. If a future change ever routes
  `/usage` (or any other text) as a literal prompt to the SDK — e.g. a
  headless/API-driven session, or the dispatcher itself changing — this
  field becomes reachable and worth a follow-up to render a structured
  usage card from `usage_report` instead of relying on the assistant's
  plain-text fallback. Documented in detail under "## SDK changelog
  highlights" above so a reviewer can re-check the audit if that
  assumption changes.
- None of the hook-timeout changelog items needed Claudius code, but
  they're worth a mental note for anyone debugging a hung `Stop`/
  `SessionStart` hook after this upgrade: the CLI now treats a timed-out
  callback as "no decision" rather than "failure", which can change
  which hook's decision wins when multiple `Stop` hooks are registered
  (relevant to any user-configured hooks surfaced via Claudius's
  `/hooks` viewer, even though Claudius's own programmatic hooks don't
  use these events).
