# SDK update 0.3.296 → 0.3.301

## Summary

0.3.296 → 0.3.301 is a small window: per-tool permission policies on sdk-type MCP server configs (`tools`), `BUILTIN_TOOL_NAMES` / `LEGACY_TOOL_NAME_ALIASES` exports, `reloadPlugins({ addPlugins })`, an optional `nextFireAt` on the CronCreate/CronList outputs, and a handful of CLI-side fixes. Claudius adopted two things: the cron `nextFireAt` is plumbed from the structured `CronCreate` result into the Activity rail's loop chip ("next in 17m"), on both the client reducer and the server-side loop mirror; and a vitest drift guard checks the restricted-mode deny list against the new `BUILTIN_TOOL_NAMES` / `LEGACY_TOOL_NAME_ALIASES` exports. Everything else is absorbed as type-only or skipped with an audit result. Headline risk: `nextFireAt` is a creation-time snapshot, so the chip is hidden once it passes (it does not track later fires of a recurring job).

## Code changes

- `lib/shared/session-loops.ts` — added optional `SessionLoop.nextFireAt` and the pure helper `readCronNextFireAt(toolUseResult)` (accepts only finite positive epoch-ms numbers).
- `lib/client/types.ts` — added optional `ScheduledLoop.nextFireAt`.
- `lib/client/use-session.ts` — the CronCreate tool_result promotion now reads `tool_use_result.nextFireAt` and stores it on the promoted loop.
- `lib/server/session.ts` — the server-side `trackScheduledLoops` mirror does the same, so the `/api/schedule/session-loops` payload and replay carry the value (the `/schedule` page does not render it yet); also imports `readCronNextFireAt`.
- `components/panels/widgets/ScheduledLoops.tsx` — new `data-testid="loop-next-fire"` chip ("next in 17m"), shown for non-cancelled cron loops while `nextFireAt` is still in the future.
- `tests/unit/restricted-mode.test.ts` — drift guard for `RESTRICTED_MODE_DISALLOWED_TOOLS` against `BUILTIN_TOOL_NAMES` / `LEGACY_TOOL_NAME_ALIASES`.
- `tests/unit/cron-next-fire.test.ts` — unit coverage for `readCronNextFireAt`.
- `tests/e2e/sdk-update-0.3.301-cron-next-fire.spec.ts` + `docs/sdk-updates/0.3.301/cron-next-fire.png` — e2e + screenshot for the new chip.

## Risks / follow-ups

- The `/schedule` page's session-loop rows do not render `nextFireAt` yet (the API payload carries it); adding it there would be a second UI surface.
- `nextFireAt` is read once at CronCreate time. For a recurring job the chip vanishes after the first run rather than tracking later fires; a follow-up could refresh it from `CronList` results when the agent calls it.
- The chip relies on the structured `tool_use_result` accompanying the CronCreate tool_result; if the CLI stops forwarding that sibling field the chip silently disappears (no text-parse fallback, since the result text carries no timestamp).
- `BashOutput` in `RESTRICTED_MODE_DISALLOWED_TOOLS` is not in `BUILTIN_TOOL_NAMES` or the legacy alias map; left in place (harmless) and whitelisted in the new test. Worth pruning in a future cycle if confirmed gone.
- Opportunity not taken: sdk-type MCP `tools` permission policies could let Claudius force `always_ask` on future in-process MCP servers.
