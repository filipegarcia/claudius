# SDK update 0.3.314 → 0.3.316

## Summary

0.3.315 and 0.3.316 are parity bumps (Claude Code v2.1.315 / v2.1.316). The only type-surface additions are the host-only `permissions.blockReadsExemptPaths` setting and the `pending_elicitation_requests` field on the `initialize` control response. Neither is reachable from, or useful to, Claudius's current call path (see below), so this PR is a dependency bump plus these notes with no product-code changes. Headline risk: low; the only judgment call is not exposing `blockReadsExemptPaths`, documented under follow-ups.

## SDK changelog highlights

- `permissions.blockReadsExemptPaths` on `Settings` (changelog + `.d.ts`) — [skipped — the SDK documents it as read ONLY from `--settings` and settings the host sends mid-session, and ignored in user/project/local/managed settings. Claudius's settings/permissions UI edits user/project/local files (`lib/server/settings.ts` `updatePermissions`, `app/[workspaceId]/permissions/page.tsx`), so a toggle there would write a key the CLI ignores. Claudius's only host-settings channel is the programmatic `settings:` object in `lib/server/session.ts`; adding a user-facing exempt-path list there is a new feature with its own UX/security surface (path validation) and is deferred. Existing `blockReadsOutsideWorkingDirectories` toggle is unchanged and still correct.] No model-identity surface involved.
- `blockReadsExemptPaths` (new declaration, `sdk.d.ts`) — same item as above; [skipped — host-only, not honored from the settings files Claudius edits].
- `pending_elicitation_requests` (new declaration on `ControlResponse` / success `initialize` response) — [skipped — internal control-protocol field for a client that *joins an already-initialized* CLI process and needs to re-arm in-flight MCP elicitations. It is not plumbed to any public `query()` option or return value Claudius consumes (verified by grep: Claudius reads neither this field nor its siblings `pending_permission_requests` / `pending_user_dialog_requests`). Claudius is the sole host that spawns the process and already tracks MCP elicitations itself via `Options.onElicitation` (`session.ts` `mcp_elicitation_request` + replay buffer), so there is no late-joining SDK client to serve.]
- "Updated to parity with Claude Code v2.1.315" / "v2.1.316" — [skipped — no consumer-facing API change; the raw `.d.ts` diff contains only the items above plus JSDoc rewording.]
- Doc-only changes in the raw diff (`bashEditDiffEnabled` default text now "off, except in auto and bypassPermissions modes…"; `blockWritesOutsideWorkingDirectories` JSDoc; `SDKMessageOrigin.subkind`/`fireReason` and `UserPromptSubmitHookInput.source` wording "routine" → "scheduled task") — [type-only]. `bashEditDiffEnabled` is already in `SDK_SETTINGS_CATALOG` as a plain boolean; its default description was reviewed and no behaviour in Claudius depends on the old default wording.

## Code changes

- No code changes required. Both new public declarations are either host-only settings Claudius's file-based editors cannot meaningfully set, or a control-protocol field not exposed through the public API.

The only diff beyond the dependency bump (`package.json`, `bun.lock`, already committed) is this run-notes file. No model name, alias, default model, context window, capability tier or pricing tier changed in this window, so no model surfaces needed auditing beyond confirming the diff contains no `Settings.model*`/pricing/`ModelInfo` changes.

## Risks / follow-ups

- `permissions.blockReadsExemptPaths` could later be exposed as a host-side setting (passed via the `settings:` option in `session.ts`, not written to user/project/local files). Assumption: skipping is the conservative choice; rejected alternative was adding it to the permissions page, which would write a key the CLI ignores.
- If Claudius ever supports attaching a second client to a live CLI process, `pending_elicitation_requests` (alongside `pending_user_dialog_requests`) would be the way to re-arm in-flight elicitations.
