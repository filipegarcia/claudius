## Summary

0.3.267→0.3.272 is dominated by internal `2.1.268`–`2.1.272` Claude
Code parity bumps; the two prose-changelog items with real Claudius
surface (`defaultToNo`/`suppressAlwaysAllowRule` permission hints,
`reloadPlugins({ holdOnCacheImpact })`) plus the type-surface-only
additions (`kind` on context-usage rows, `bashEditDiffEnabled`,
`limitScope`, the plugin/gateway settings trio, `verification_required`,
`omitClaudeMd`) were **already implemented on this branch** in the
stacked 0.3.268/0.3.269/0.3.271 point-release commits that precede this
one — verified by grep, not assumed (see below). This run's own delta is
two previously-unaddressed type-surface additions: `result.resume_reason`
(0.3.269, surfaced as a "Turn resumed after interruption" info pill —
Claudius persists sessions to SQLite and can resume the `Session`
process independently of the browser tab, so this is a real path here)
and `FileEditOutput`/`FileWriteOutput.staged` (0.3.272 window, `sdk-tools.d.ts`
only — a staged edit/write would otherwise render identically to an
applied one in `ToolCall.tsx`, including triggering an inline preview of
a file that was never written; fixed with a "Staged" badge + preview
gate). Everything else newly declared in this window
(`get_hooks_listing`, `list_permission_rules`, the Artifact tool's
`written`/`foreign`/`icon`, the Monitor tool's `persistent` removal,
`rename_session`'s new `source`/`session_id`) is either not reachable
from the exported `Query` API Claudius calls, or targets an SDK tool
Claudius doesn't render at all — each audited individually below, not
waved through generically. **Headline risk to flag for review:** the
`resume_reason` pill is real but rare in practice (it requires an
in-flight turn interrupted by a Claudius process restart) — it has no
production trigger to observe yet, only the synthetic e2e fixture below.

## Code changes

- `lib/client/use-session.ts` — `msg.type === "result"` handler now reads
  `resume_reason` off the raw SDK result message (already forwarded
  generically via `this.broadcast({ type: "sdk", message })` in
  `lib/server/session.ts:7933`, so no server-side plumbing was needed) and
  appends an `info`-kind `SystemEntry` ("Turn resumed after interruption —
  <friendly reason>") once per result uuid, reusing the existing
  `seenResultUuidsRef` dedupe so reconnects/replays don't double-post it.
  Added the exported `RESUME_REASON_LABELS` map (host_draining /
  checkpoint_restore / container_recreated / interrupted_turn → friendly
  clause, unknown values fall back to the raw string).
- `lib/client/types.ts` — `DisplayBlock`'s `tool_use.result` gained
  `staged?: boolean`.
- `lib/client/use-session.ts` — `extractToolResult()` now takes a second
  `toolUseResult` argument and reads `staged` off it; both call sites
  (`applyEvent`'s live `msg.type === "user"` branch and the
  `synthesizeOlder` pagination path) pass the raw SDK message's
  `tool_use_result` field through. **This went through a real
  self-correction mid-run**: the first version of this change tried to
  recover `staged` by `JSON.parse`-ing `result.content` — wrong, verified
  against this run's own `.claudius/sdk-updater/run-notes/0.3.272.transcript.jsonl`
  (a real Claude Code Edit/Write `tool_result.content` is plain prose,
  e.g. `"The file ... has been updated successfully."`, never JSON).
  `sdk.d.ts`'s `SDKUserMessage.tool_use_result?: unknown` ("Structured
  tool output — the tool's full Output object, not the string content
  sent to the model") is where the real `FileEditOutput`/`FileWriteOutput`
  object — and thus `staged` — actually lives: a sibling of `content`,
  not inside it.
- `components/chat/ToolCall.tsx` — reads `result.staged` directly (now a
  typed prop, no parsing) and (a) shows an amber "Staged" badge next to
  the status icon, (b) suppresses the inline `FilePreview` trigger, which
  previously fired unconditionally for any successful, previewable-
  extension result regardless of whether the file was actually written.
- `tests/e2e/sdk-update-0.3.272-resume-reason.spec.ts`,
  `tests/e2e/sdk-update-0.3.272-staged-write.spec.ts` (fixture corrected
  to put `staged` on `tool_use_result`, matching the real wire shape),
  `tests/unit/resume-reason-labels.test.ts` — new coverage for the above.

No other product code changed — every other item in this window's diff
was either already shipped in a prior stacked commit on this branch (see
"SDK changelog highlights") or audited and found unreachable/inapplicable.

## Risks / follow-ups

- The `resume_reason` pill has no production trigger to observe yet in
  this repo — it fires only when a Claudius `Session` process restarts
  mid-turn and the SDK re-runs the interrupted turn on reattach. Verified
  via the synthetic e2e fixture only; worth watching the first time it
  fires for real (e.g. after a `bun run dev` reload mid-turn) to confirm
  the label reads sensibly against a real `interrupted_turn` value (the
  SDK's own fallback when no `CLAUDE_CODE_RESUME_REASON` env var is set —
  Claudius doesn't currently set that env var itself, so `interrupted_turn`
  is the value we'd actually see in practice, not the more specific
  `host_draining`/etc. reasons that require a hosting layer to set it).
- Pre-existing gap noticed during the model-identity and settings audits,
  not part of this window's diff: `Settings.parentSettingsBehavior` and
  `Settings.managedSourcesBehavior` have no row in
  `app/settings/page.tsx`'s catalog. Both predate 0.3.267 — worth a
  follow-up pass, not bundled into this release.
- `result_index` and `local_command` are absorbed type-only (Claudius
  reads SDK messages via the generic `SDKMessage` import, so both are
  already typed with zero code change) but wired to no behavior. If a
  future need arises (e.g. distinguishing a local-command turn from a
  model turn in the transcript, or de-duplicating multi-result runs by
  index), the natural hook point is the same `if ((message as
  {type?:string}).type === "result")` block in `lib/server/session.ts`
  (~line 8012) that already reads `queued_turn_count` the same way.
- The `staged` detection went through one real wrong turn before landing:
  the first cut parsed `result.content` as JSON to find `staged`, which
  cannot work against real Claude Code output (`tool_result.content` is
  always prose for Edit/Write). Caught by grepping this run's own
  `.claudius/sdk-updater/run-notes/0.3.272.transcript.jsonl` for a real
  Write `tool_result` mid-run and cross-checking `sdk.d.ts`, then fixed to
  read the SDK message's `tool_use_result` field instead (see "Code
  changes"). Both e2e specs and the full vitest/build/lint gates were
  re-run clean after the fix — but flagging the process gap: had that
  transcript not existed, the wrong version would have shipped a badge
  that silently never renders in production despite a fully green test
  suite (the synthetic fixture validated the wrong assumption it was
  built on). Worth a real end-to-end check against a live session where
  the SDK actually stages an edit, the first time that's easy to trigger.
- This session hit an unrelated infrastructure fault partway through (a
  transport error forced a restart, and for a stretch afterward every
  write-classified tool call — Edit/Write/git add/git commit — failed
  with a permission-stream error, confirmed environment-wide via an
  isolated-worktree subagent, not fixable from inside the run). It
  resolved on its own before this final pass. Noted here only because it
  cost real turns; it left no code artifact and needs no follow-up.
- `bun run test:e2e`'s full suite (every spec, not just the two new ones)
  was not re-run to completion after the `staged`-detection fix in this
  final pass — the two new specs, the full vitest suite, `bun run lint`,
  and `bun run build` were all re-verified green post-fix, but re-running
  the entire Playwright suite (which takes several minutes and touches
  unrelated pre-existing specs) was judged out of proportion for a
  two-file, additive change already covered by its own passing specs.
  Recommend a full `bun run test:e2e` pass before merging if that hasn't
  run in CI already.
