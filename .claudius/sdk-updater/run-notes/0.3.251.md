## Summary

The upstream changelog for 0.3.251 is a single line ("Updated to parity
with Claude Code v2.1.251"), but the `.d.ts` diff adds two real
control-protocol hook events, `PreModelSwitch` and `PostModelSwitch`,
fired around every mid-session model change (picker, `/model` command,
headless `sdk` caller, automatic `fallbackModel` swap, or a resumed
session landing on a different model than requested). We mirror both
into the `/hooks` editor's event list (`lib/shared/hook-events.ts`,
new "Model switching" category), and we register `PostModelSwitch` as
an in-process observer hook in `lib/server/session.ts` — filling a real
gap: Claudius previously had **no signal at all** for an automatic
`fallbackModel` swap mid-turn (the code's own `opusOverloadStreak` doc
comment already called this out as "swaps silently"). The hook now
keeps `this.model` / the SSE `model_changed` broadcast / (for durable
sources) `sessions.model` in sync, and the client raises a toast
("Automatic fallback (rate limit)") instead of leaving the user to
notice a different model only once responses come back changed. We
deliberately do **not** register `PreModelSwitch` in-process — its
`permissionDecision` contract makes it an extension point (allow/deny/
ask), and the file already carries a hard precedent
(`WorktreeCreate`/`WorktreeRemove`) that a passive observer on an
extension-point hook breaks the feature outright. The hook's decision
logic is extracted into a pure, exported `resolvePostModelSwitchHook`
function so it's unit-tested directly (9 cases) rather than only
type-checked. The rest of the
version's type surface (artifact-tool fields, the Remote Control
bridge's `onSetModel` return shape, `SessionStartHookInput`'s new
cache-timing fields, and the `AgentDefinition`/`AgentInfo`/`AgentInput`
model-doc rewording) audited out to genuinely unreachable — see below
for the specific evidence per item. **Headline risk for review:** the
`resolvePostModelSwitchHook` decision logic is unit-tested, but the
hook actually *firing* from a live SDK process for the `auto`/`resume`/
`sdk` sources is not — that needs a real rate-limit fallback or a
resume landing on a mismatched model, neither reproducible headlessly.
See "## Risks / follow-ups".

## Code changes

- `lib/shared/hook-events.ts` — add `PreModelSwitch` / `PostModelSwitch`
  to `HOOK_EVENT_NAMES`, `HOOK_EVENTS` (new `"model"` category), and
  `CATEGORY_LABELS`/`CATEGORY_ORDER`, so the `/hooks` editor lists both
  new SDK hook events like every other SDK hook event.
- `lib/server/session.ts` — register a `PostModelSwitch` hook (pure
  observer) alongside the existing `PreToolUse`/`PostToolUse`/
  `CwdChanged` hooks. The decision logic (which sources qualify, which
  model to adopt, whether to persist) is extracted into a standalone
  exported function, `resolvePostModelSwitchHook(input, currentModel)`,
  next to the existing `worktreeRootFromPath` pure-helper precedent —
  the hook closure itself only does the side effects (assign
  `this.model`, broadcast, conditionally `upsertSession`). Gated on
  `source` (`"auto" | "resume" | "sdk"` only — never `"picker"`/
  `"command"`, which the existing `setModel()` and chat-command-regex
  paths already cover) so it can never race or double-broadcast against
  those two paths. Persists to `sessions.model` for `resume`/`sdk`
  sources only (an `auto` fallback is transient and shouldn't become
  the sticky resume default — see Risks).
- `lib/shared/events.ts` — widen `ModelChangedEvent.source` to
  `"picker" | "chat_command" | "auto" | "resume" | "sdk"`.
- `lib/client/use-session.ts`, `lib/client/types.ts`,
  `components/chat/ModelChatCommandNoticePanel.tsx` — extend the
  existing chat-command model-switch toast with a `reason:
  "chat_command" | "auto"` field so an automatic fallback raises its
  own toast ("Automatic fallback (rate limit)") through the same
  component, rather than adding a sibling component for a single new
  copy variant.
- `tests/unit/hook-events.test.ts` — two new pinning tests, mirroring
  the existing `DirectoryAdded`/`PostToolUse` regression-guard pattern
  for this SDK bump's two new events.
- `tests/unit/session-model-switch.test.ts` (new) — 9 cases against
  `resolvePostModelSwitchHook`: all three qualifying sources, both
  ignored sources, the duplicate-fire/no-op-switch/empty-model guards,
  and the `undefined`-current-model edge case.

## Risks / follow-ups

- **The `PostModelSwitch` hook actually being invoked by a live SDK
  process is unverified.** `resolvePostModelSwitchHook`'s decision
  logic (source gating, model/persist selection, the three no-op
  guards) is unit-tested against the `.d.ts` shape directly, and the
  hook registration around it type-checks — but no test drives a real
  `fallbackModel` swap or a mismatched resume through an actual
  `query()`, so the *wiring* (is `PostModelSwitch` really delivered to
  this callback the way `PreToolUse`/`PostToolUse`/`CwdChanged` are?)
  is unverified. If the SDK's real firing conditions differ from the
  `.d.ts` in practice, this would silently no-op rather than error
  loudly. Worth a manual smoke test against a session configured with a
  `fallbackModel` the next time a rate limit is reproducible.
- **`PreModelSwitch` is deliberately not registered in-process.** If a
  future feature wants pre-switch confirmation (e.g., warn before a
  cache-cold, costly switch using `estimated_cache_write_usd`), this is
  the extension point — but per the `WorktreeCreate`/`WorktreeRemove`
  precedent, it must return a complete `permissionDecision` contract,
  not a passive `{ continue: true }`.
- **`auto`-sourced switches are intentionally not persisted** to
  `sessions.model` (only updated in memory + broadcast). This is a
  deliberate choice, not an oversight: persisting a transient
  rate-limit fallback would make it the sticky resume default even
  after the rate limit clears. `resume`/`sdk` sources ARE persisted
  since they reflect a durable state change. Flagging in case a
  reviewer expects symmetric persistence across all three new sources.
- **`defaultSubagentModel` concept referenced in this release's doc
  rewording doesn't exist as a field anywhere in the SDK yet** (see
  audit above) — revisit `AgentDefinition`/`AgentInfo`/`AgentInput`
  handling once it ships as an actual `Settings` key.
