# SDK update 0.3.220 → 0.3.221

## Summary

0.3.221 is a small, internal-only release: it tightens validation of
the top-level `Options.skills` field (malformed/wildcard-form names
now throw a clear error instead of being silently tolerated, and
`skills: 'all'` is documented as the explicit "enable everything"
value) and fixes external MCP servers passed via `Options.mcpServers`
not being connected before the first turn. **No Claudius code changed
for this release.** Both items were audited against every place
Claudius touches the two fields, including reading the compiled SDK
bundle (`sdk.mjs`) directly rather than trusting `sdk.d.ts` comments,
and neither has a reachable call site: Claudius never sets
`Options.skills`, and the only entry in `Options.mcpServers` we pass
is an in-process SDK server, not an external one. We did initially
suspect a hit on `AgentDefinition.skills` (a same-named but distinct
sibling field used per-subagent, fed from user-submitted JSON in
`lib/server/db-agents.ts`) and shipped a defensive filter for it —
but reading `sdk.mjs` showed the new validator (`Oxe`) is called
exactly once, from the `Options.skills` → `allowedTools` transform,
and never touches `AgentDefinition.skills`. That fix would have
silently dropped legitimate skill names (e.g. `"pdf*"`, `"a:b:c"`,
`"has space"` are all valid per the SDK's own denylist) to guard
against a validation path that doesn't exist for that field, so it
was reverted before landing. Headline risk to flag: none — this is a
verified no-op release for Claudius; see the audit trail below for
what was checked.

## SDK changelog highlights

- **Improved `skills` option validation** (malformed names — delimiters
  or control characters — and wildcard-form names now rejected with a
  clear error; `skills: 'all'` documented as the explicit
  "enable every skill" value).
  `[skipped — audited, no call site, verified against compiled SDK]`
  Claudius never sets the top-level `Options.skills` in
  `lib/server/session.ts` (`rg -n "skills\s*:" lib/server/session.ts`
  — no hit); we always omit it, which the SDK docs (`sdk.d.ts`
  line 1916-1917) state is "not skills off" — the CLI's own defaults
  apply, i.e. every discovered skill loads already, behaviourally
  identical to `skills: 'all'`. We also never pass `'Skill'` inside
  `allowedTools` (the other deprecated path this option replaces).
  During audit we suspected a second call site — `AgentDefinition.skills`,
  a distinct field (`sdk.d.ts` line 67, `string[]` only, no `'all'`
  form) that `lib/server/db-agents.ts` `coerceAgentDefinition()` builds
  from arbitrary JSON reaching `PUT /api/agents/db`
  (`app/api/agents/db/route.ts`), filtered only by
  `typeof === "string"`. We initially shipped a defensive skill-name
  format filter there as a hedge — then read
  `node_modules/@anthropic-ai/claude-agent-sdk/sdk.mjs` directly (not
  just the `.d.ts`) and found the new validator function, paired with a
  control-character denylist regex (rejecting parentheses, commas, and
  C0/C1 control characters), is called **exactly once** in the whole
  bundle: inside the `Options.skills` destructure, mapping each entry
  through the validator and wrapping it as a `Skill(name)` entry
  appended to `allowedTools`. It is never invoked for
  `AgentDefinition.skills`. So the sibling field isn't validated by
  this change at all, and our filter was solving a problem that
  doesn't exist — worse, it was stricter than the SDK's own rules
  (e.g. it rejected `"pdf*"`, `"a:b:c"`, and `"has space"`, all of
  which the real SDK-side denylist accepts), so it would have silently
  dropped legitimate skill names from stored agent definitions.
  Reverted before landing — `lib/server/db-agents.ts` and its test are
  byte-identical to `main`.
- **Fixed external MCP servers passed via the `mcpServers` option not
  being connected before the first turn** (previously caused the model
  to emit tool calls as literal text).
  `[skipped — no call site]` Audited every place Claudius passes the
  `mcpServers` option and every other `query()` call site in the repo
  (`lib/server/session.ts`, `lib/server/scheduler.ts`,
  `lib/server/commit-message.ts`, `lib/server/session-recap.ts`,
  `lib/server/customization-description.ts`,
  `app/api/models/probe/route.ts`, `lib/server/updater/apply.ts`).
  Only `lib/server/session.ts:2086` sets `Options.mcpServers`, and it
  passes exactly one entry, `claudius_goal`, built by
  `buildGoalMcpServer()` via the SDK's own `createSdkMcpServer()` — an
  **in-process** `McpSdkServerConfigWithInstance`, not one of the
  `McpStdioServerConfig` / `McpSSEServerConfig` / `McpHttpServerConfig`
  "external" (process-transport) shapes this changelog item is about.
  Workspace/file-configured MCP servers (`.mcp.json`, `settings.json`
  `mcpServers`, read/written by `lib/server/mcp.ts`) are never merged
  into the initial `Options.mcpServers` — they're read by the CLI
  subprocess itself, a separate path entirely. Runtime-added servers go
  through `Query.setMcpServers()` post-start
  (`lib/server/session.ts:4680`, `Session.setMcpServers`), also a
  distinct API from the startup option this bug fix targets. No
  external/process-transport server is ever handed to `Options.mcpServers`
  at session start, so this connection-timing bug has nothing to fix in
  Claudius.

## Code changes

- No code changes required. Both changelog items were audited to
  their exact SDK-side implementation (`sdk.mjs`, not just `sdk.d.ts`)
  and confirmed to have no reachable Claudius call site: we never set
  `Options.skills`, and the only `Options.mcpServers` entry we pass is
  an in-process SDK server. A defensive fix to `lib/server/db-agents.ts`
  was written and then reverted after the `sdk.mjs` read showed it
  guarded a validation path (`AgentDefinition.skills`) the SDK doesn't
  actually touch in this release — see the changelog section above for
  the full trail. `lib/server/db-agents.ts` and
  `tests/unit/db-agents-coerce.test.ts` are byte-identical to `main`.

## New UI surfaces

- No new UI surfaces this release. Both changelog items are
  server/CLI-internal (an SDK-side option validator and an MCP
  connection-timing fix) with no Claudius call site, so nothing a user
  sees or does in the browser changed.

## Tests

- No new tests required. No code changed (see above); the one test
  case written during the initial (later-reverted) defensive fix was
  reverted along with the code it covered, so
  `tests/unit/db-agents-coerce.test.ts` is unchanged from `main`.

## Risks / follow-ups

- No migration risk identified. Both changelog items were traced to
  their exact implementation in the compiled SDK bundle
  (`node_modules/@anthropic-ai/claude-agent-sdk/sdk.mjs`) rather than
  inferred from the `.d.ts` or changelog wording alone, which is what
  caught the near-miss described above (a defensive fix that looked
  reasonable from the type signature but was wrong once checked
  against the actual validator). If a future SDK release's changelog
  extends this validation to `AgentDefinition.skills`, that would be a
  new, real call site worth revisiting at that point — it doesn't
  exist yet in 0.3.221.
- Unrelated pre-existing e2e flakiness observed while gating this PR,
  worth a follow-up independent of this release: three separate full
  `bun run test:e2e` runs each turned up 2-3 failures, but a different
  set each time (`sdk-update-0.3.219-workflow-size-guideline.spec.ts`,
  `session-tab-switch.spec.ts`, `notifications-multi-tab.spec.ts`,
  `session-tabs-new-button-position.spec.ts`,
  `cc-parity-2.1.207-disable-auto-mode.spec.ts`,
  `turn-status.spec.ts`), and every failing spec passed cleanly when
  re-run in isolation. The dev machine had a load average of ~35-40
  during these runs (an unrelated background process), which is the
  likely cause — these specs have tight timeouts (button-enabled
  waits, `waitForURL`, SSE-stream polls) that don't leave headroom
  under CPU contention. The final gating run used `CI=1` (which the
  project's own `playwright.config.ts` already gates retries on,
  specifically for "timing-sensitive on slower runners" flakes per its
  existing comment) and came back clean: 180 passed, 7 skipped, 3
  flaky-but-recovered-on-retry, 0 failed. No test code changed to
  reach this result. Worth revisiting whether any of the 6 specs above
  should get slightly more generous local timeouts independent of this
  release. Note for whoever triages this PR: if the orchestrator's own
  post-return `bun run test:e2e` (run without `CI=1`, per its default
  invocation) shows a red gate, that is very likely this same
  environmental flakiness recurring, not a regression introduced here
  — the diff contains zero product code, only the version bump and
  these run-notes. Re-running the specific failing spec(s) in
  isolation is the fastest way to confirm before assuming a real
  break.
