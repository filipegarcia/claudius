# SDK update 0.3.263 → 0.3.267

## Summary

This window is dominated by parity bumps (2.1.264–2.1.267) and two real SDK
changes: the `systemPrompt` recording default flipped to "record by default"
(Claudius already opted out of this explicitly back at the 0.3.265 bump, so
it needed no new code), and `user_message_uuid`/`user_message_uuids` gained a
"re-stamp on each answered-message change" semantic that Claudius's only
consumer (`idle-reconcile.ts`) already treats as idempotent. The `.d.ts` diff
adds a `Settings.maxEffortLevel` org/user effort ceiling (shipped — a new
enum row in the settings catalog, matching the existing `effortLevel` row)
and a `cloud_credential_error` variant of `SDKAssistantMessageError` (shipped
— a friendlier retry-banner phrase). Everything else under "New declarations"
(the `sdkMcpServerManifests` control-protocol field, `Transport.markDelivered`,
the two new `project_memory_*` tool methods, `ArtifactOutput.seq`/`unchanged`,
and the whole `browser-sdk.d.ts` SSE-resume surface) is verified unreachable
from any Claudius call site — see the per-item audits below. Headline risk
for review: none of the shipped changes touch a hot path (settings catalog
row, error-copy lookup), so the main thing to sanity-check is that the new
`maxEffortLevel` catalog row's Playwright spec actually exercises the
save/clear round trip against the real `/api/settings` endpoints.

  `auth-failed-detector.ts`, `long-context-credits-detector.ts`,
  `use-session.ts`) do `===`/lookup-with-fallback, not an exhaustive switch,

## Risks / follow-ups

- `ApiRetryErrorReason` (`lib/client/api-retry.ts`) is still missing
  `'account_on_hold'`, a pre-existing gap unrelated to this bump (it
  predates 0.3.263). Not fixed here to keep this diff scoped to the actual
  0.3.267 changes; falls back to the generic "a temporary error" copy today,
  same as `cloud_credential_error` did before this PR. Worth a follow-up
  pass over the whole `SDKAssistantMessageError` union.
- `maxEffortLevel`'s clamp semantics are enforced entirely by the CLI/SDK
  (across every settings source, "lowest wins"); Claudius's new settings row
  only lets a user *set* the value; it doesn't surface the effective clamp
  anywhere in the effort-picker UI (e.g. graying out an effort level above
  the ceiling). Not attempted here — the SDK doesn't expose "here's your
  effective ceiling" to a running session, only the raw settings value, so
  there's no data to compute that UI from.
- None of the four gate commands surfaced a pre-existing failure unrelated
  to this bump.
